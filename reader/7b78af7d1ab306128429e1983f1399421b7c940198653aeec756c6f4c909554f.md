### 多人软件工厂的张力与演进

欢迎来到我们关于多人软件工厂的分享。在这场演讲中，我将带大家了解当多个人和多个 Agent 在同一个软件交付流水线上协作时，会产生哪些张力，又有哪些解决方案。软件交付流水线当然不是什么新鲜事物，在 AI 出现之前就已存在。大家所熟知的典型流程是构建、测试，然后等待发布以及合并到主分支（main）。这基本上是一个串行流程，它帮助我们实现了交付的自动化并提升了稳健性。与此同时，人们正在构建我称之为“单人工厂”（solo factories）的系统——在自己的笔记本电脑、自己的系统上，在编码 Agent 内部运行；并且大家越来越多地使用多个 Agent，通过 Agent 来进行交付。现在，人类往往仍需做出决策，也必须执行合并，在某种程度上扮演着核心角色，几乎就像必须由人类来留存各项操作的记忆一样。我今天所讲的不是单人模式，而是多人协作模式。这中间或许存在渐进的演变阶段：目前人们在自己的笔记本电脑上运行；接着是人们在工厂内部共享配置，比如上下文、技能（skills）以及循环机制（loops），这大致是当下许多工厂的状态；再之后则是多人工厂——大家在同一个工单看板、同一个代码库上同时协同工作。这就是我今天将为大家梳理的内容。在左侧，张力来自于每个人都想合并到 main；在右侧，看板上有多个人，大家必须协同配合。这就是本次演讲的两个组成部分。

### 从持续交付到并发交付

那么，为什么我们不能扭转这种局面，让并发从一种偶发异常变成常规流程呢？这就是我所称的“并发交付”（concurrent delivery）——从持续交付（continuous delivery）迈向并发交付，专为人类与 Agent 在同一代码库上协同工作而设计。现在，我们可以做的一件简单事情是：与其单纯地让 Agent 并行运行，不如更聪明地处理。这几乎就像我们按单元拆分工作一样，比如你负责这个任务，你负责那个任务；我们可以通过不同的拆分方式规定：你负责身份认证，我负责支付，我负责其他部分。我们甚至可以利用 AST（抽象语法树）图来判断哪些部分非常适于拆分。然后，我们可以让 Agent 进入更细粒度的层级，指定“这个文件、这个函数”，它们甚至可以精确到某些击键操作，比如在某些文件中一起协作编辑。这是一种在实际编码之前对工作进行更多切分的方法，是一种规划变更的更优途径。

### 意图冲突与推测式合并队列

你可以看到的一点是，Agent 已经被针对合并代码进行了优化，对吧？代码合并层面上这是清晰明了的。但如果两个变更同时提交落地会怎样？举个例子：你在计算并修改发票总额的计算函数，假定单位不仅是美元，还改成了美分。与此同时，有另一个 PR 更改了报表输出的逻辑。这两个合并在代码层面上完全一致、能够顺利合并，并且测试全部通过；但在同一时刻，两者的意图却产生了分歧——报表并不希望以欧分或美分为单位显示，对吧？所以它们在代码上没有冲突，但在意图上产生了冲突。因此，我们可以让 Agent 去检查意图在多个合并之间是否依然保持一致，并向我们发出警告，或相应地调整 PR。如果想要开始执行合并，这些 PR 已经具备合并条件，可以合并了。但是，如果其中某个合并未能顺利完成呢？那你通常必须对所有其他 PR 进行 rebase，它们必须返工等等。处理这些合并队列（merge trains）有一种更好的方式，那就是引入一个名为“推测式合并队列”（speculative merge trains）的概念。它会审视所有进来的 PR，分析哪些 PR 彼此兼容，并预先进行成对校验。随后它判断出：当那个 PR 正在合入、而这个 PR 无法合入时，其他 PR 依然可以继续合入；这样整体速度就更快了，因为所有能够通过的 PR 已经在合并队列中继续推进了。这些只是应对合并、冲突、代码审查以及更好规划的一些新策略示例。我认为总体而言，一层新的基础设施层正在形成。你几乎能从各大供应商那里看到这一点，你知道，这是一种全新的开发者基础设施——合并将以不同的方式处理，现在有了分析能力，有了更优的规划，对各项事务都有了更好的工具。而这正是我们目前正在构建的。当前许多工厂还只是我们在 CI/CD 中所做的那种美化版的循环（glorified loops），但并发度只会不断提高。

### 人机协同与工单细化

现在，正如我之前所说，这件事情还有另一面：不仅是 Agent 在协同，人类也在协同工作。通常的变化在于大家是在同一个任务看板中协作，对吧？所有人类成员都能看到即将到来的变更是哪些、正在处理的任务是哪些。这创造了可见性；而在你的单人工厂里，你完全是独自进行操作，并不是在这样一个中央看板上工作。现在，它们都需要引起你的注意，而这大概是比较容易的部分，对吧？因此我们也希望减少这种注意力消耗，避免 Agent 动辄就需要呼叫你。这是多个 Agent 同时工作时产生的一个副效应。令人欣喜的特性之一是——看到 Agent 能够加入你的群聊是非常有意思的，这是一种不同的编码方式。它不再是由你单向发出 prompt，而是你将一个 Agent 拉入对话中。这非常强大，因为 Agent 不仅能从你这里获取线索，还能同时从你的团队成员那里获取线索。它实际上正在做的是根据所有输入来细化完善工单。这极其强大，因为你不仅拥有了 Agent 开展的对抗性审查（adversarial review），而且在对话进行期间，多个人类针对同一张工单贡献的输入也能汇聚进来。而它非常擅长的一点是以提问的方式向你索取反馈，而不是反反复复追问所有事情。因此，有帮助的一点在于它能澄清测试是什么、应该做些什么、需要达成的需求是什么。此时工单实际上几乎变成了类似于你编码 Agent 里的“规划模式”（plan mode），但现在它作为看板内的共享功能存在，供大家审视所有需求。

### 人机断点接管与决策日志

有时 Agent 在执行过程中会拿不准，你可能也有同感：有时工厂内部的工单模式比较慢，而你希望进行快速迭代。现在有一种混合处理的方法——比如当你的 Agent 卡住时。Helix ML 提出了一个非常有趣的方案：当你的 Agent 卡住时，它实际上会启动一个新的编码 IDE，其中包含 Agent 当时处理的精确上下文；作为人类的你几乎可以直接切入进去，借助所有可用的上下文和各类现成文件，帮助 Agent 理清思路；然后，当你做出了正确的选择、完成了合适的实验后，再把它交接回给 Agent 和工厂继续运行。这是一种在个人编码 Agent 的快速迭代与依托工厂运行之间寻找折中平衡的极佳方式；Agent 同样可以利用这一点来明确疑问、获取帮助以及请求协助。

### 基于风险的代码审查机制

我们希望变更保持小巧，因为大型变更的可读性很差。所以，虽然我在开篇提到你可以针对避免 Agent 冲突进行优化，但还有另一件事你必须考虑，那就是人类的审查：一个人类能审查多大体量的变更？你可以构建独立的 PR 并纳入多条主合并队列中，以便人们对这些内容进行快速审查。现在很多人关注的是：当 PR 产生且我们希望减少 PR 审查次数时，引入某种自动化审查。第一部分通常是减少故障，这很棒，对吧？我们希望提供更好的上下文、更优质的工具，在代码提交给我们之前让对抗性 Agent 预先检查代码，这是通过提升质量来降低风险的良好方式。与此同时，我们也在优化让我们能直观看到它做了什么：我们要求提供屏幕流程截图、录屏视频、证据、测试等所有能对审查人员有所助益的内容。那么归根结底，你要深入到什么程度？有几个人跟我说：“嘿，我已经不看代码了。”我问他们：“好吧，但这个变更上线到生产环境的影响是什么？”某些文档变更的影响是有限的；可能有些项目并没有真实客户，这也很好，对吧？其影响并不大。但如果你真正深入思考自己在做什么，你其实是在根据自己能够承担的风险来进行筛选。因此，某些测试会判定：如果是在文档部分，你可以直接放行；如果是像身份认证内部这样故障影响更大的变更，你就需要安排更多的人工审查；有时也存在中间方案——这个功能可以直接发布，我们通过渐进式发布来监测输出结果以及是否存在报错。因此，除了单纯针对质量进行优化以降低发生概率之外，你还可以从风险的视角来看待它。

### 组织协同与工厂平台团队

在多人工厂中工作，一件颇有意思的事情是：在此之前大家是在群聊沟通，以我个人为例，我是远程办公，而团队大部分成员集中在伦敦的一处办公地。他们聚集在一起，会有大量的群聊互动等等，而身处远端的我有时的确很难跟上变化节奏。现在，一旦开启多人工厂，每个人都需要跟上节奏，对吧？产出的代码如此之多，以至于市场、客服支持以及其他部门可能根本无法跟上。他们需要将发生的变化翻译成符合他们语境的语言。因此，沟通与扩散同步变化（radiating change）实际上是多人工厂中一项极其重要的功能：你如何在自己的领域内、以符合你理解的方式，跟进关乎你工作职责的那部分内容？概括而言，你可以做大量的自动化工作，你会运用许多技能，依靠上下文以及对这些环节的更好改进，并把人类精力留给异常情况。这就是我希望大家去思考的方式：尽你所能实现自动化，但确保具备路由给人类的能力，以便依托所有这些基础设施以及所有这些协同工作方式，做出正确的决策。
