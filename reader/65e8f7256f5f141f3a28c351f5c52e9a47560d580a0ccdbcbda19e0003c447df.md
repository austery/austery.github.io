### 异步任务的起源与长期运行挑战

模型上下文协议（Model Context Protocol）的异步任务（Tasks）规范自发布起即备受关注，但客户端的实现却面临重重挑战。核心原因在于，传统的**请求-响应**（Request-Response）模式无法有效支持需要长期运行（Long-running）的复杂业务。

以一个采购订单（Purchase Order）的处理流程为例：当系统接收到订单后，需要并行执行多项任务，如记录货物已接收、更新后台库存、发送通知以及通过 MCP 工具处理发票支付。其中，发票支付本身是一个包含 ERP 系统校验、人工审批（Human in the loop）以及对账等多个子步骤的长生命周期流程。在异步任务模式下，调用该工具时客户端不会阻塞等待最终结果，而是立即获取一个任务句柄（Handle），以便后续跟踪和交互。

### 韧性架构与分布式故障应对

在长周期执行的过程中，任务面临着极高的基础设施故障风险。这包括网络瞬断、负责审批的人员离线或休假、以及客户端或 MCP 服务端的意外崩溃。

为保障业务连续性，MCP Tasks 规范的核心设计原则是**持久化**（Durability）：
* 一旦异步任务启动，其生命周期状态必须在服务端持久化，绝不能因连接中断或进程重启而丢失。
* 基础设施恢复后，客户端必须能够凭任务句柄重新与该任务建立关联并恢复上下文。

通过 FastMCP 编写的客户端与服务端演示表明，即使在后端服务器尚未启动时，前端提交的采购订单仍能被正确缓存。在服务重启并恢复后，工作流能够精准定位此前挂起的“需要输入”（Input Required）状态，在接收到审批批准信号后，继续驱动底层的重试逻辑直至最终支付完成。

### 协议痛点与无状态化革命

在 MCP Tasks V1 协议中，系统通过一个复杂的**状态化协议**（Stateful Protocol）来维护任务生命周期，这在大规模分布式场景下暴露了严重的设计缺陷：
* **任务列表终结点的扩展性灾难**：在 V1 中，如果客户端重连，会通过 `tasks/list` 向服务端查询当前所有任务。由于该终结点没有设计过滤机制，当后台有数百万级（Millions of tasks）任务并行执行时，客户端拉取并遍历百万级任务数据的开销是无法承受的。
* **长连接交互的脆弱性**：在 `input-required`（等待输入）状态下，协议要求客户端与服务端之间维持长连接，由服务端主动向客户端索取数据。这种双向互动的复杂设计，使得连接一旦中断，状态的对齐和恢复极其脆弱。

针对上述缺陷，即将发布的 **MCP Tasks V2** 协议引入了**无状态核心**（Stateless Core）的设计，将 Tasks 重新定位为协议的模块化扩展（Extension）：
1. **废除 `tasks/list`**：彻底移除了在大规模场景下不可行的任务列表查询接口。
2. **引入单向更新信号**：取消了服务端向客户端索取数据的长连接模式，改为引入类似于工作流引擎中 **信号**（Signal）机制的更新接口（`update` 终结点），允许客户端以无状态的单向请求向服务端推送状态更新。
3. **优化结果获取逻辑**：保留任务结果（`result`）接口，但彻底剥离了此前长会话的耦合，使通信模式更加扁平高效。

### 职责转移与百万级扩容展望

在 V2 协议取消了 `tasks/list` 查询接口后，系统的状态管理职责发生转移：
* **客户端本地持久化**：客户端被赋予了在本地持久化存储任务 ID（Persist Task IDs）的职责。如果客户端未能保存这些 ID，在系统重连后将无从寻回正在运行的异步任务。
* **并发处理能力提升**：V1 客户端的引用实现通常只能以先进先出（FIFO）的队列串行处理挂起的任务；V2 借助无状态的信号推送，使得大规模并发处理与响应多个任务成为可能。

针对百万级（Millions of tasks）任务运行的极端规模场景，即使采用无状态请求，逐一轮询（GET）每个任务的开销依然非常庞大。为了解决扩展性问题，协议未来将依赖于**通知协议**（Notifications Protocol）。客户端通过订阅统一的通知接口来获知“是否有任务的状态发生变更”，并仅在接收到变更事件时，才发起针对具体任务的拉取请求，从而极大地降低网络流量。

在生态建设方面，开发团队计划在近期将完整的无状态异步任务处理机制无缝集成至 **FastMCP** 框架中，使开发者能够延续现有的开发模式，降低构建高可用异步 MCP 服务的门槛。
