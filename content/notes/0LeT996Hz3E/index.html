软件工厂的基础设施架构分层

那么这到底是什么样子的？如果你从第一性原理思考如何工程化一个 Agent 系统，我认为会得出类似这样的架构。不一定完全一致，但这是一种可用于工程化你的 Agent 的基础设施技术栈。

  • 工厂即代码（Factories as Code）：处于该架构的最底层，我前面提到过。即以代码格式定义你所有的编码 Agent 工作流。这样做的好处在于，你获得了以此为基础拉取分支并测试不同工厂配置的能力，你还可以执行回滚。最关键的是，它为自我改进开辟了道路，即让编码 Agent 自身对工厂的运作方式提出修改建议，从而让这种持续闭环运转起来。
  • 数据与上下文层（Data and Context Layer）：在底层之上是数据和上下文层，这同样至关重要。如果你在组织内规模化运行编码 Agent，你确实必须记录这些 Agent 所产出的一切内容：包括它们的所有对话、所有工件（artifacts）、它们制作的视频以及截图。这样做的原因在于，这些是随着时间推移用来改进工厂运作方式的原材料。
  • 计算层（Compute Layer）：其上是计算层。你需要具备沙箱环境（sandboxing）。沙箱提升了安全性，使你的工厂更具可复现性。你的沙箱可能应该是多平台的。
  • 推理与模型层（Inference Layer）：再往上是推理层。在工厂中看待推理和模型的方式，是将它们视为用于测试的自由度。因此，无论你的工厂如何构建，都应该支持多种模型。它还应该支持多种编码 Agent，因为 Claude Code 可能在某些方面表现更好，还有 Codex、Py、Warp 等。这些框架（harnesses）具有不同的特性。你可能想要编写自己的编码 Agent 框架，将组织内部的部分上下文嵌入其中。所以平台应该对此提供支持。
  • 编排层（Orchestration Layer）：在这之上，你需要一个编排层。这正是实际推动工作在工厂中流转的组件。从某些角度来看它是最乏味的部分，但你必须拥有它。
  • 接口与集成层：最后，你的工厂应该完全遵循 API 与 MCP 优先，这样它不仅能被人使用，也能被其他编码 Agent 使用。并且它可以深入到具体工作发生的场景中，因此你的工厂应该与 Slack、Linear、Jira、GitHub 等工具进行集成。

Doesn't have to be exactly this, but uh, it's kind of an infrastructure stack that uh, that you're going to want to use to engineer your agents.
