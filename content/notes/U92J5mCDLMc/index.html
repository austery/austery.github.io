Cognition：通过软件工厂与目标导向 Agent 实现 40 倍工程吞吐量提升

关键字 autonomous-agent software-engineering ai-tooling developer-productivity

摘要

Cognition 联合创始人兼首席产品官 Walden 阐述了其团队如何在工程团队人数增长 2.7 倍的情况下将合并 PR 吞吐量提升 40 倍。核心举措包括将团队重构为拥有端到端职责的小组、让 Devin 自主运行从 Bug 报告到合并监控的“软件工厂”、基于 Docker Compose 与本地 Mock 构建无需依赖云端实时服务的沙箱与每小时重建镜像，以及将给 Agent 下发具体任务转变为赋予长期目标（如系统延迟调优、GPU 吞吐优化和 Android 应用对齐）。

构建端到端自动化的软件工厂

在座很多人可能都熟悉“软件工厂”（Software Factory）。你们当中有多少人听说过软件工厂？大家举下手看看。太棒了。那么我先从基础概念讲起，然后再逐步深入到更高阶的内容。

英文原文 Many of you are probably familiar with the software factory. How many of you guys have heard of software factory? Let's see a raise of hands. Cool. So I'll start with the basics and then I'll work my way up to the more advanced stuff.

软件工厂的基本理念是：是的，默认情况下一切都应该是自动驾驶的。我们有许多 PR，从最初的 Bug 报告到最终的合并、监控和维护，全程没有任何人类参与。当然，通常需要人类判断介入时，我们就会有升级机制。但在默认情况下，我们的整个开发流程就是由 Devin 从头到尾端到端运行的。

英文原文 The basic idea of a software factory is yeah, by default everything should be self-driving. We have PRs that go from initial bug report to final merge and monitoring and maintenance without a single human involved. Often time, human judgment is needed, though, and that's where we have escalations. But by default, our entire development process is just run by Devon from end to end.

这意味着一件事情：软件工程师的角色必须发生相当大的改变。大约在今年 3 月，我们与工程团队进行了这样一次对话，我们说：听着，如果你现在只是从 Linear 看板上挑选工单，然后发给 Agent 去实现，那么在 AI 时代你真的不会走向成功；因为任何只要被描述出来且能够实现的东西，都将能够交给 Devin。

英文原文 One of the things this means is that the role of the software engineer has to change quite a bit. Around March of this year, we had this conversation with the engineering team and we said, look, if you are right now just picking off tickets off a linear board and then sending that to an agent and implementing it, you're not going to really be set up for success in the age of AI cuz anything that is described and can be implemented will be able to send to Devon.

所以实际上，每个人都必须改变自己的开发方式。我们推行这一点的方式是：把原有的大团队拆分成更小的 Pod（小组）。

英文原文 So really, everyone has to change the way that they're developing. And the way we've enforced this is we've taken our larger teams and we've broken them up into smaller pods.

这些更小的 Pod 不仅配备了成群的 Agent 来为他们工作，而且被赋予了更多的纵向职责。所以相反，你一个团队一次可能只有两到三名工程师，但除了工程本身之外，他们还要对所有事情负责：他们负责倾听客户的 Bug 报告，负责做 QA 测试，负责做 PM 和产品管理；基本上每位工程师都管理着自己一整套待办事项的 Linear 看板，并把这些发给 Agent 去替他们实现。因此，这确实是我们工程师工作方式的根本性转变。这是我们在过去一年中落地的举措之一，而且我们也一直在帮助很多大型组织为他们自己落地这套模式。

英文原文 And these smaller pods not only are given swarms of agents to do work for them, they are given more vertical responsibility. So instead, you might have only two or three engineers on a team at a time, but they're responsible for everything beyond the engineering as well. They're responsible for listening to customer bug reports. They're responsible for doing QA testing. They're responsible for doing the PMing and product management and basically every engineer manages their entire own linear board of things to do and they send that to an agent to implement for them. So it's really a fundamental change in the way that our engineers do work. This has been one of the things that we've implemented over the last year and we've been helping a lot of large organizations implement for themselves as well.

基于 Slack 与本地沙箱的免 IDE 开发

我还非常想强调的另一件事是：我们无处不在使用 Slack 工作。这是一个客户 Bug 报告可能是什么样子的示例：他们在 Slack 上给我发来一段视频，我们直接把 Bug 报告转发到内部频道，然后 @Devin 说：“嘿，请修一下这个。”Devin 会立刻响应，提交一个 PR，但同时还会回传一段附带修复和证据证明的视频。

英文原文 Another thing I'd really like to highlight is we work from Slack everywhere. So this is an example of what a customer bug report might look like. They send me a video on Slack and we just forward bug reports straight into our internal channel and we tag Devon and say, hey, please fix this. Devon immediately comes up, shows up a PR, but then also sends back a video with the fix and proof.

这让我们的生活轻松了太多，因为在大多数时间里，我真的不需要离开 Slack……我们把所有的开发流程都抽象为基于证据和视频，直接把修复完成的证据发回给客户，大部分时间甚至都不需要打开 IDE 或者 GitHub。

英文原文 And this makes our lives so much easier because I literally don't have to leave Slack for most of my We've abstracted away all the development to be based on evidence, videos, and just send the proof that the fix is ready right back to the customer without having to open an IDE or even GitHub most of the time.

所以这就是你希望达到的终极目标：在这样一个节点上，你无需打开 IDE，甚至无需打开任何一个编程 Agent，就能完成整个开发生命周期。

英文原文 So this is kind of the end goal you want to reach, which is a point where you can do your entire development lifecycle without opening up an IDE or without opening up a single coding agent.

但要达到这个阶段，我们在底层必须对大量基础设施进行改造。如果每个工程团队想要达到那种状态，这正是真正必须攻克的困难部分。这绝不是买一个编程 Agent 就完事了，你必须去改变你的构建方式。以前我们测试应用时，都是针对云端部署环境进行测试：我们会有一个预发布环境（staging），连接到 staging 数据库，连接到线上服务器，然后让我们的工程师手动去逐项点击，端到端验证流程是否正常。

英文原文 But to get to this point, there was a lot of infrastructure we had to change underneath. And so this is the hard part that really every engineering team has to do if they want to get to that point. It's not just you purchase a coding agent, you got to go change the way you build. So before when we tested our applications, we'd be testing them against cloud deployments. We'd have a staging environment, connect to a staging database, connect to live servers, and then we'd have our engineers manually go click through and verify that the flows work end to end.

我们做了一次大规模迁移：将每个服务都改造成能够通过 Docker Compose 在本地运行。我们做到了让我们拥有的每一个第三方服务都有 Mock 版本，能够在本地跑起来。这些服务全都可以跑在单台虚拟机内部，每个 Devin 都可以访问这台虚拟机。而我们公司现在的每一个编程 Agent 在测试其修改时，完全不需要接触任何线上实时服务。

英文原文 We did a big migration to move every service to be able to run locally with Docker Compose. We've made it so every third-party service we have mocked versions to be able to run locally. And these could all run inside a single virtual machine that every dev in has access to. And every coding agent in our company now does not need to touch any live services at all to test their changes.

事实上，在公司里，我们每小时都会重建这些虚拟机。每隔一小时，我们拉取最新版本的代码，从零开始重新构建整个代码库，以便能够非常快速、轻松地从零运行。如果因为代码库变化太快导致这些构建失败，我们也会让 Devin 作为第一响应者；它们总是立即去修复这些虚拟机快照。因此，每次我们从 Slack 启动一个 Agent 时，它都会进入一台全新的机器，基于带有最新更新的代码库的全新版本运行。

英文原文 They In fact, these VMs, we rebuild them every hour at the company. Every hour we pull the latest version of the code, we rebuild the entire codebase from scratch to be able to run very quickly and easily from scratch. Um and if these builds ever fail because your codebase is rapidly changing, uh we also have dev in be the first response there. And they're always immediately fixing these VM snapshots. So every time we spin up an agent from Slack, it goes to a fresh machine on a fresh version of the codebase with the latest updates.

顺便提一句，这些 Agent 你也需要教会它们如何测试你的代码库。但使用云端编程 Agent 的好处在于，它们可以自我维护其训练闭环。所以最后关于测试的那一部分：Devin 会自己编写关于如何测试我们代码库的技能（skills）。代码库会随着时间变化，测试它的方式也会改变，但 Devin 可以持续更新这些 skills，从而反复对它进行测试。

英文原文 Um and by the way, these agents you need to teach them how to test your codebase as well. But the benefit of using cloud coding agents is that they can self-maintain their training loops. So that last section there on testing, dev in will write its own skills for how to test our codebase. The codebase will change over time, so the way you test it will change, but Devon can keep on updating these skills so that test it over and over again.

这带来的最终结果就是：大家在测试任何代码变更时，真的再也不需要打开笔记本电脑了。事实上，Cognition 的好几位工程师在他们的开发流程中已经转为使用 iPad 了。

英文原文 So the end result of this is literally people do not need to open their laptops anymore to test any code changes. In fact, several engineers at Cognition have already moved to using iPads for their development process.

顺便说一下，iPad 也更安全。大家知道，最近看到了很多黑客攻击事件，其中很大一部分是因为 DevOps 以及人员泄露密钥。谁知道你开发者的机器上有些什么？你可能到处都留有各种密钥。当一切都在云端这些受控的虚拟机中运行时，你实际上处于一个安全得多的境地。

英文原文 By the way, iPads are also more secure. You know, a lot of you see a lot of these hacks recently, a lot of it is because of DevOps and and people leaking keys. Who knows what's on your developer machine? You might have secrets all over the place. Uh when everything is in the cloud with in these controlled VMs, you're actually in a much more secure spot.

递归自我优化与从任务到目标的范式转变

我刚才展示了一些能够测试的基础场景。我们其实还测试过高级的多人协作环境，这非常酷。以前在开发 Devin 加入语音和 Zoom 通话的能力时，我们实际上让 Devin 在测试期间创建多个账号，让它们从同一台虚拟机内部加入同一个 Zoom 通话，并来回发送语音备忘录，以确保功能正常工作。所以如果你真的去拓展代码库的边界，你可以做到相当高阶的配置。

英文原文 Um I've shown some basic versions of things you can test. We've also tested advanced multiplayer setups, which is really cool. We've often times when we were developing Devon's ability to join voice and Zoom calls, we actually had Devon when it tests create multiple accounts, have them join the same Zoom call all from within their one VM and send voice memos back and forth to make sure that the functionality is working. So you can do quite advanced setups if you really push the limits of your code base.

不仅如此，在此基础之上，显然你还会希望实现递归的自我优化。我认为人们往往过多地从模型层面来思考这个问题。但实际上仔细想想，在云端 Agent 的配置下，被写下的每一行代码、生成的每一个 PR、做出的每一个决定，都会在整个代码库中被全程追踪。所以完全没有理由不在其之上运行 Agent，去做数据分析，找出我们在哪里浪费了时间、在哪里浪费了 Token、哪些东西可以被做成脚本，以及我们可以添加哪些测试来改进这个流程。

英文原文 Um and it actually on top of all of this, you know, you obviously want recursive self-improvement. I think people think about this from the model sense quite a lot. But actually, if you think about it, every single line of code that's being written, every single PR that's being generated, every decision, if you have a cloud agent setup, that's all tracked across your entire code base. So there's no reason why you shouldn't also be able to run agents on top of that, do the data analysis and figure out where are we wasting time, where are we wasting tokens, what you know, things can be turned into scripts, what tests can we be adding to improve this process.

因此我们有一个频道，Devin 每天都会在里面发布想法，比如：“嘿，如果我们更改 Node 的配置，CI 就可以节省大约一分钟时间；如果我们修改这个 lint 脚本，就能在这些 Bug 进入 AI 代码审查之前多捕获 20%。”这实际上带来了巨大的突破，你可以直接搭建好这些系统，Agent 就会去替你优化你的软件工厂。

英文原文 And so we have a channel where Devon every day posts ideas about, hey, if we change our node setup, we can shave like a minute off of our CI. If we change this lint script, we can like catch 20% more of these bugs before they ever hit AI code review. Um and this is actually been a huge unlock and where you can just set up these systems and the agents will go and optimize your software factory for you.

这真的让人非常兴奋。我平时没怎么听大家谈论、但我认为确实是未来发展方向的事情之一，就是从给 Agent 分配任务（tasks）的世界，走向给 Agent 分配工作（jobs）的世界。这是一次范式转变。你真的必须开始把它们当作同事来看待。那么，给 Agent 分配一份工作具体是什么样子的？

英文原文 Um this has been really exciting. One of the things that I don't hear people talking about a lot, but I think it's really where things are going next is moving from the world where you're giving tasks to your agents to giving jobs to your agents. And this is a bit of a paradigm shift. You you really have to start treating these things like co-workers. So what is giving a job to an agent look like?

设想一下我很在乎后端性能。未来的开发流程实际上应该是这样的：你应该发消息给你的 Agent：“嘿，我想提升我们应用的 P99 延迟。”不用你去告诉它具体做些什么来达成这一点，它应该回复：“好的，P99 延迟，让我先添加遥测监控，搞清楚我们目前的 P99 延迟处于什么水平；让我设置告警，明确我们未来需要达到什么目标；让我去把能够优化该延迟所需的所有单项任务拆解出来；让我创建 Datadog 告警；让我在 Slack 中生成周报，并且每天在手机上向你同步最新进展——比如目前的 P99 延迟是多少、已经提升了多少。”

英文原文 Imagine I care about back-end performance. Really this is what the development flow of the future should look like. You should send to your agent, hey, I want to improve P99 latency of my application. Instead of you telling it what to do to do that, it should say, okay, P99 latency, let me add the telemetry to figure out where our P99 latency is today. Let me set up alerts so I can figure out where we need to be in the future. Let me go break down every single task we need to do to be able to move this latency. Let me create DataDog alerts. Let me create weekly reports in Slack and let me send you updates on your phone every day on here's where a P99 latency is and here's how much it's improved.

这从根本上就是我们在 Cognition 鼓励所有工程师去构建的系统类型。在大部分时间里，我们甚至都不希望你去给 Agent 写 Prompt。我们希望你只是给 Agent 设定目标，让它们在很长的时间跨度内奔着目标去工作。

英文原文 This is fundamentally the type of systems that we encourage all of our engineers to be building at Cognition. We don't even we don't even want you to be prompting your agents most of the time. We want you to just be giving your agent goals that they can work toward over long durations of time.

而在你们公司里，任何你认为无法衡量的东西，都要想办法去衡量它。你关心你的应用性能吗？去测量你应用上的点击延迟；如果你的应用有很多奇怪的布局位移（layout shifts），去测量 bounding box，尝试找出如何尽量减少整个应用的布局位移。显然除了 P99 延迟，还有像新手引导留存率这样的指标。你们作为工程师所做的事情中，有多少是可以归纳为一个单一数字或指标的？我鼓励你们，如果能够做到这一点，你们就应该直接配置一个 Agent，去 7x24 小时不断优化那个数字。

英文原文 And anything in your company that you think isn't measurable, find a way to measure it. You know, do you care about your application performance? Go measure, you know, the latency of clicks on your application. If your application has a lot of weird layout shifts, go measure the bounding boxes and try to figure out how you can minimize layout shifts across your application. There's obviously P9 9 latency, but there's also things like, you know, onboarding retention. How much of what you guys do as engineers is things you can boil down to a single number or metric? And I encourage you that if you can do that, you should just set up an agent to go optimize that number 24/7.

实践案例：GPU 吞吐优化与全自主 Android 开发

关于这一点，一个极佳的例子就是推理延迟。在 Cognition，我们很幸运地成为了英伟达新一代 Vera Rubin GPU 的首批接收者。我们拿到这批 GPU 时，内核还没为它们构建好，所以我们必须从零开始摸索如何在这些新推出的硬件之上构建我们自己的推理技术栈。而 Agent 让我们能够以比以往高效得多的方式完成这项工作。

英文原文 So a great example of this is inference latency. At Cognition, we're lucky to be the first receivers of Nvidia's new class of Vera Rubin GPUs. Kernels were not built for these GPUs when we received them. So we had to from scratch figure out how do we build our own inference stack on top of this this new hardware that's coming out. And agents have allowed us to do this in a way that is much more efficient than before.

所以，我们只是告诉它：“嘿，我们关心这些 GPU 的吞吐量，也就是我们的 TPM。去搞清楚如何把它推向极限。”在大概（我猜在这里）大约一周的时间里，Agent 能够——我们给它分配了一组固定的 GPU 供其使用——它能够去探索不同的策略并进行测试；对于它发现效果最好的策略，它会提交给人类工程师做最终审批。通过仅给这些 Agent 设定高层级目标，基本上大致发现了八到九种不同的方案。

英文原文 So, we just tell it, hey, we care about the throughput, our TPM of these GPUs. Go figure out how to push that to its limits. And over the course of what is about, I guess here like a week, um the agent was able to go We We allocated it a permanent set of GPUs to work on. It was able to go find different strategies, test them. Uh the strategies that it found worked best it was sent to a human engineer for final approval.
