托管智能体的五大核心支柱

这里展示的是构成托管智能体的基础构建块，也就是几个不同的核心支柱：

  • 测试框架（Harness）：即 anti-gravity harness。它与 Google 内部 anti-gravity 系列产品中运行的完全是同一个 harness，负责解析和决策工具调用，并提供内置工具。
  • 环境（Environment）：环境本身是一个独立的实体。它支持实现非常强大的多智能体工作流：你可以让不同的智能体指向同一个沙箱，某个智能体在其中写入文件，后续另一个智能体可以接手同一个环境并基于这些文件继续构建。
  • 技能（Skills）：你可以把技能上传到沙箱中，就像你在公司或个人智能体中定义的行动手册（playbooks）或特定工作流程一样，这些都可以直接上传到托管智能体中。
  • 凭据管理（Credentials）：这是托管智能体的一项新功能，它允许我们将令牌（tokens）或 MCP OAuth 凭据注入到托管智能体沙箱中，以便访问各类外部服务。
  • 触发器（Triggers）：允许你设定定时任务来调度托管智能体。例如每天早上 8:30 开盘前，你希望进行某种金融分析，就可以设置触发器。托管智能体到时会自动唤醒，执行任务或处理输入，并输出结果。你可以配置 Webhook 发送 Slack 消息；也可以让它每天早上查询团队的 Jira 看板，汇总并发送大家的工作进展等。

在托管智能体的 agent config 配置中，你可以通过一行参数来指定模型，从而根据具体工作流进行调优：如果任务追求速度与高效率，可以使用 Gemini Flash；如果需要进行深度推理或海量数据分析，则可以切换为像 Gemini 4 Argon 这样的模型。

Gemini 4 模型另一个非常强大且有趣的特性是长解码（long decode）。通常情况下，模型的输出 token 上限大约在 64K 左右；但在 Gemini 4 中，我们将这一限制放开，现在 100 万 token 的上下文窗口限制是由输入（input）、思考（thinking）和输出（output）共同共享的。因此，当你的输出需求需要扩展——比如进行极其复杂的数学推理或金融建模，输出可能长达数十页时——模型完全有能力直接生成。这已经被证明能够显著提升相关数学与金融评测基准的表现。

Interactions 与 Environments 原语

刚才我们探讨了 Interactions API 与环境（environments），它们是托管智能体的两大核心原语，赋予了系统极高的灵活性与配置自由度。

这两者是我们服务端后端维护的两种不同状态实体：

  • Interactions（交互）：用于管理对话状态。当你输入内容、获取输出，并与模型进行一轮轮对话时，这些轮次会被保存为所谓的 interactions。你可以提取上一个 interaction 的 ID 并传给下一个 interaction，以此构成第二轮对话。
  • Environments（环境）：代表云端沙箱文件系统中的实际内容。当智能体在云端沙箱中写入文件、生成图像或执行各种文件任务时，这些就构成了环境状态。你可以通过我们的 API 从该环境中下载或上传文件。

将这两者解耦可以带来非常强大的能力。如图中的第一段代码所示，我们创建了一个智能体 interaction，它开始执行工作并保存了一个文件；随后，我们可以把该 environment ID 传递给下一个智能体。下一个智能体接手时，拥有全新的上下文窗口和对话空间，但却能直接复用同一个文件环境。例如，前一个智能体抓取年报与报备文件，将 Q3 财报保存到工作空间并完成部分分析、存为文件；随后新智能体介入，复用完全相同的物理环境，但拥有干净的上下文窗口。这构成了一种非常优雅的多智能体协作工作流。

安全架构与多智能体编排

托管智能体在安全性方面的另一大关键设计是：机密信息（secrets）绝不会真正进入沙箱。

我们的托管智能体系统在沙箱与 API 之间部署了一层代理（proxy）。该代理在沙箱中放置一个占位用的伪令牌（dummy token），这样智能体就绝不可能“失控反叛”并心想：“既然手头有个 GitHub 令牌，让我看看还能读取什么其他数据。”因为真实的 GitHub 令牌根本不在沙箱里，它无法执行未授权操作。当智能体发起对 GitHub API 的调用时，我们的代理层会进行拦截匹配，识别出目标是 GitHub API，再由代理注入真正的密钥。这样便能严格杜绝智能体越权操作。

英文原文 So, another big part of the security aspect of managed agents is that secrets never actually enter the sandbox. So, our managed agents have a proxy that sits uh it's a kind of a layer between the sandbox and our API.
