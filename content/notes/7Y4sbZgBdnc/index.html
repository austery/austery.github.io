术语演变与 Harness 架构解构

从生成式 AI 的发展脉络来看，行业角色与核心概念经历了一场深刻的重构：2023 年初，提示词工程（Prompt Engineering: 编写和优化输入指令以引导大模型输出期望结果的技术）曾是最炙手可热的岗位；到 2025 年中，这一角色演化为上下文工程（Context Engineering: 通过程序化方式动态整合并向模型输入最精准上下文的技术）；而直到今年初，整个行业才正式确立了 Agent Harness（智能体脚手架/运行载体: 包裹在模型外部、负责连接真实世界并控制其行为的系统框架）以及相应的 Harness 工程体系。从架构本质而言，Harness 扮演着模型的眼睛与双手——它负责引导模型走向，通过应用程序接收用户意图，并将底层模型与操作系统、外部计算环境以及各类 MCP（Model Context Protocol: 模型上下文协议，连接第三方服务与数据源的标准化通信协议）第三方服务无缝接入。

在技术架构划分上，完整的 Harness 可清晰地拆解为两大核心层级：

  • 运行时层（Runtime Layer）：整个 Harness 的工程地基。它严格控制 Agent 核心循环的执行环境、运行状态的持久化存储以及任务的中断恢复机制。这部分的工程构筑与传统软件工程的底层系统建设高度一致。
  • 上下文与编排层（Context and Orchestration Layer）：行业中最常讨论且变化极为剧烈的部分。该层级负责动态决策何时调用特定模型、精准注入何种上下文信息（涵盖提示词、工具集、内存压缩策略），并包含大量用于纠正模型不良行为的专有工程技巧。

今年年初，整个生态一度迎来了 Harness 的狂热巅峰：Cursor 曾发布通过名为 Grind Swarm 的长周期多模态 Harness 从零构建完整浏览器的案例，该架构编排调度了庞大的多智能体与物理机器集群，算力开销极其惊人，甚至在实机演示期间多次导致服务过载。

模型进化与代码能力平庸化：Harness 的消亡假说

在经历 Harness 的巅峰期后，业界迅速掀起了一股“Harness 已死”的反思思潮。Anthropic 的工程师 Tariq 曾公开表示他们在 Claude Code 中大幅精简乃至剔除了大量原本复杂的系统提示词；Y Combinator 的 Garry Tan 亦断言复杂的 Harness 将逐渐淡出舞台，未来唯有轻量化的 Skills 具有核心价值。即便是 Cursor 团队自身，也逐步剥离了早期为了修补基础模型智力短板而设置的大量硬性防护栏——例如过去为了准确应用文件代码修改而额外调用的轻量代码专用模型，以及硬编码在提示词中指导模型如何检索代码库、如何自我校验的繁琐指令。

多项严谨的基准评估也为这一趋势提供了量化支撑：

  • SWE-bench Light 基准测试：加州大学伯克利分校（UC Berkeley）针对七大前沿模型在不同 Harness（包括 Pi、Codex、Claude Code）下的表现进行了全面横评。结果表明，在最新一代更聪明的模型加持下，底层 Harness 的复杂程度与测试得分之间已不存在显著的统计学差异。
  • MLE-bench 评估实验：来自苹果公司（Apple）与洛桑联邦理工学院（EPFL）的联合研究同样揭示，专为机器学习工程打造的专用 MLE Harness 并未对基准测试结果带来实质性的提升。

这些事实清晰地证明：在当前技术阶段，复杂的 Harness 已不再为编码任务注入额外的纯模型智力。过去人类工程师在 Harness 中精心设计的“思维补丁”——教导模型如何分步探索大型代码库、如何通过持久循环长时间坚守任务、如何执行单元测试以验证交付结果——如今已被前沿大模型的原生权重与推理链路完整吸收内化。

数据飞轮效应：旧 Harness 的自我消解机制

为什么旧式专注于补全模型智力的 Harness 会不可避免地走向自我消亡？这源于系统层面的数据飞轮（Data Flywheel: 技术工具降低高难度任务门槛，产生高质量交互数据反哺基础模型，从而使工具本身被模型替代的正向反馈循环）。这种演进遵循着高度确定性的因果链条：

  1. 拓宽解决边界：在特定历史阶段，工程团队构建高度复杂的 Harness 与规则补丁，使模型能够勉强胜任原本无法独立完成的硬核编程任务；
  2. 释放用户生产力：更广阔的能力边界吸引了海量真实开发者在日常工程中深度使用 Agent 解决复杂代码问题；
  3. 高质量数据回流：海量用户在复杂任务中的探索轨迹与修复记录回流至各前沿 AI 实验室；
  4. 模型原生吸收能力：各大前沿实验室通过后训练（Post-training）与强化学习将这些工作范式完整内化为基础模型的原生直觉；
  5. 脚手架冗余淘汰：最终，模型在脱离复杂约束的情况下依然能高效完成任务，原先 Harness 中用于维系这些任务的冗余逻辑和外挂补丁便可被安全删除。

由此可见，Harness 在特定领域内的消亡并非技术的退步，而是其成功履行历史使命的必然结果。然而，这绝不意味着 Harness 本身失去了存在价值——当纯粹的基础编码能力被模型彻底平庸化（Commoditized）后，Harness 必须且正在承担起全新的战略使命：开拓模型尚未征服的下一代未知任务前沿，并承担起大模型无法独立内化的生产级基础设施与工程底座。

开辟未知前沿：从 GrokBot 架构看第二曲线

当单一的代码生成逐渐标准化，新一代产品如 GrokBot 正在展示 Harness 的破局之路。GrokBot 被定义为一个全自动化的协作数字同事，其覆盖范围已远远跨越了传统的代码补写，拓展到了全维度的复合型知识工作。其底层的 Harness 彻底摒弃了传统的“单次短对话”范式，转向由长期驻留的协调智能体（Coordinator Bot）统领离散工作智能体集群（Fleet of Worker Agents）的编排架构。其分工协作类似于资深合伙人律师负责与客户高层直接对接、把控整体战略方向，而将具体的法律调研与案头文书分发给一众初级律师团队执行。

极为耐人寻味的是：在 Cursor 的后期演进中，工程团队一直在持续删除 Harness 层的提示词与规则栏；但在开发 GrokBot 时，团队却反向大量重新引入了严密的提示词约束与行为护栏。其根本原因在于，在这个全新的交互范畴中，模型在面对现实复杂协作时暴露出海量未经锤炼的新型缺陷：

  • 复合网页交互流：自主协调制作完整的演示文稿（Slide Decks）或处理跨平台的商务差旅预订；
  • 非侵入式进度通报：智能体必须具备高维度的自我汇报纪律，在保持异步前行的同时向人类透明反馈关键进展，避免信息轰炸；
  • 行动与询问的边界博弈（Acting vs. Asking）：在涉及给真实同事发送电子邮件等高风险行为时，自主决断在何种阈值下应主动执行、何种情况下必须挂起确认；
  • 跨周期记忆网络（Long-term Memory）：持续感知并内化特定人类用户的隐性协作偏好与组织惯例。

这些挑战补齐了数据飞轮的最后一环：一旦模型平庸化了上一代核心能力（如纯粹的局部编码），唯有依靠新型 Harness 构建脚手架，才能带领模型强行涉足尚未被数据充分覆盖的高难度新任务，进而重新引爆新一轮的数据积累与能力内化循环。在全生命周期的软件开发中，资深工程师的核心时间原本就极少消耗在单纯的敲代码上，代码之外的架构抉择、端到端协作与排障调度才是更大的蓝海。

软件工厂与不可替代的基石：环境、信任与工程效率

除了驱动未知场景，Harness 另一个不可被模型吞噬的维度体现在软件工厂（Software Factory: 多个自主智能体分工协同、闭环覆盖软件工程全生命周期的工业化生产体系）所要求的实体工程底座上。在企业内部实践中，一个标准的自治链路正在形成：当用户在协作频道中提出 Bug 时，自动化模块完成首次分类与定级；紧接着触发云端独立的修复 Agent 编写补丁，并通过专用工具链生成修改前后的录屏视频以证实修复结果；一旦补丁合入主干并触发自动化发布流程，Rollouts 监控产品将立即唤醒另一个专门的生产观察 Agent，全天候守护线上指标。这种跨阶段、跨工具编排的系统正是典型的元级 Harness（Meta Harness）。

这些支撑现代工业化 Agent 运行的核心能力，是底层大语言模型无论如何进化都无法单凭文本概率吸收的基石要素：

  1. 真实世界环境支撑（Environment）：模型本身无法自我生成隔离的云端容器、网络虚拟化拓扑与物理沙箱。没有这些坚固的环境隔离机制，任何试图脱离开发者本地笔记本长效运行的 Agent 都无从谈起。
  2. 确定性安全与信任（Trust & Safety）：尽管前沿模型号称能理解代码安全性，但企业绝不可能完全信任由非确定性神经概率生成的自主动作——将未做隔离的线上凭证、敏感密钥直接暴露给无防护的终端，无疑是灾难性的安全隐患。真正的安全防护必须由 Harness 在操作系统与执行流层级建立绝对确定的硬性拦截机制。
  3. 规模化能效工程（Efficiency & Cost）：此前引用测试虽然表明不同 Harness 在通过率上差异不大，但它们在**单任务执行成本（Cost per Task）**上却存在惊人的鸿沟。过去一个月在 GrokBot 上的实战优化显示，仅仅通过精细调节缓存命中率（Cache Hit Rate）、优化 Token 传输结构以及引入动态模型分流组合（Model Mix），便在不损耗任何交付质量的前提下，断崖式降低了使用成本并显著拉升了系统吞吐速度。随着 Agent 调用的指数级放大，底层的工程化能效比将直接决定商业闭环的生死。

Now, it could be an entire different talk about how we did this, but the key takeaway here is that the more and more that you use agents to do your work, the more it matters, the more valuable it will be for you to have the most efficient harness.

未来演进：抽象升维、事件原语与云端化未来

站在当前节点展望，整个智能体生态正步入一个全新周期：产品创新的迭代速度再次大幅领先于底层模型的迭代速度。在这段充满探索的混乱期，Harness 的设计架构正在发生几项决定性的范式转移：

  • 信息黑盒化与海姆定律的抗衡：依据海姆定律（Hyrum's Law: 只要系统的任何内部实现细节被接口暴露出来，无论文档如何规定，最终都会有外部用户依赖它），早期产品过早暴露内部状态极大制约了系统重构。在 GrokBot 等新一代方案中，底层 Harness 的复杂运转逻辑被最大程度地收敛在黑盒内部，不再直接对终端暴露细节，从而使团队能够高速发布和下线实验性功能而无需承受巨大的向下兼容包袱。
  • 构建可复用原语（Primitives）：与其为不同业务拼装离散的专用逻辑，团队正将通用需求沉淀为高度抽象的原语工具。以**订阅原语（Subscriptions Primitive）**为例：无论唤醒 Agent 的是 Slack 消息、CI 产线挂掉的警报、还是到达了特定物理时间，系统均通过统一的事件订阅框架提供原生工具接口，使 Agent 能以极简方式接入事件流。
  • 自愈型 Shim 治理机制：为了应对模型在特定边缘场景下的响应迟缓或异常，工程上不可避免需要编写一些确定性兜底补偿逻辑（被称为 Shim，如在模型延迟过高时代替用户发出微小提示）。为了防止代码库因临时补丁腐化，团队将所有 Shim 统一接入中央监控日志。部署专职机器人每日监控面板，一旦发现某项 Shim 长期零触发（意味着新版模型已自然修复该缺陷），机器人便会自动向仓库提交清理 PR，实现技术债务的自我清理。
  • 抽象层级的结构性跃迁：上一代 Harness 是将零散的基础 LLM 文本调用组合在一起；而下一代 Harness 则以完整的 Agent 作为基础积木块进行更高维度的元编排。

最终的决胜点在于运行载体的根本转变：在未来 6 个月内，90% 的生产级 Agent 任务将彻底迁离开发者的个人笔记本，全面上云运行。因为只有脱离个人设备的电量与网络限制，在弹性的云端环境中常驻，数字同事才可能达成真正的全天候自主协作。

面对最初的问题：Harness 死了吗？答案是清晰的——过去那些仅仅用来教大模型写代码的旧式脚本与琐碎防护，确实因数据飞轮而被更聪明的模型彻底淘汰；但作为连接物理世界、承载生产信任、提供极致能效比并调度多智能体未知前沿的新一代基础设施，Harness 的黄金时代才刚刚拉开序幕。

英文原文

So, by now you might be convinced that the harness still matters. Then you might be asking, "What's next?" Here's a few trends that I'm anticipating.

First of all, that flywheel is speeding up, and right now we've entered a new age where the product is once again moving faster than the model. That means that the harness is going to get more messy before it gets cleaned up. There's going to be more things shipped. So, because of this, we're expecting people to build their harnesses, design them so it's easier to ship and unship new features.

One way we're already seeing that manifest is with both Grok Bot and other similar products, less and less of the harness inner workings are being exposed to the user. Some of you may have heard of Hyrum's Law, which says that anything that you expose to users, they will come to depend on. Now, obviously there are tradeoffs to giving users less, you know, less visibility into what's happening, but one advantage is that there's less change management to deal with, and you can iterate much faster.

Now, another way that we've been seeing this trend manifest is a bigger focus on designing primitives for agents. Primitives are like building block interfaces that can be composed and extended into powerful features. When you have primitives, you can add new features without making things more complicated for the agent, and you can remove features without having to do a complicated refactor in your code base. It's just good engineering. One example across our agent harnesses of a primitive we've added is called subscriptions. Agents need a way to wake up in response to events. Those might be someone posting in Slack, CI going red on a PR that the agent cares about, or just a certain time of day. Now, rather than having one separate integration, you know, having separate integrations for each of these things, we have one framework and one tool that the model can use or the agent can use to subscribe to an event.

And then another cool thing that we do, I mentioned earlier that we have these deterministic guardrails to patch over bad behaviors in the model. That might be, for example, if GrokBot doesn't respond to the user fast enough, and we might give it a little nudge and say, "Hey, user's waiting on you." Now, we'd rather not do these things. They're kind of like hacks, but we would rather fix them now than, you know, wait for the next model checkpoint to to get released. So, in order to make our code base, you know, be less messy and and have less of a worse time iterating the future, we track all these things, which we call shims centrally, and every time the model uses one, it gets logged. So, now we have a bot who watches this dashboard, and whenever a shim stops firing, that model or that agent will put up a PR and say this shim can be cleaned up.

Another thing that I think is next for the harness is it is moving up to a higher level of abstraction. Yesterday's generation of harnesses were built from composing a bunch of LLM calls. Now, the new harnesses we're seeing, like GrokBot and the software factory, are using agents as the core building block.

And then finally, I predict that within 6 months, 90% of agent work is going to run off the laptop. This is already where things are going, and I think there's just no way that, you know, this is this is not necessary in order to have truly autonomous agents who can, you know, really work with us in in the way that we want.

So, is the harness dead? The parts that made it smarter at coding, yes, that is the flywheel at work. That is the flywheel at work. But, the harness, as we saw, is how the agents can unlock the next frontier of work. And then also the trust, the efficiency, the infrastructure that the harness brings, those things are not going anywhere. So, yesterday's harness may be dead, but long live the agent harness of tomorrow. Thank you.
