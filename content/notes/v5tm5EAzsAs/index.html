代码与运行时的脱节：Trace 成为新的事实来源

为了弄清我们错在哪里，在于我们做出了一个不切实际的假设：假设错误会发生在代码层面。但错误极少发生在代码层，相反，这些 Agent 是在运行时发生故障的。

英文原文 So, to understand where the mistake that we made is is we made an unrealistic assumption. And that assumption is that the error is going to occur at the code, but the error rarely occurs at the code level. Instead, these agents are failing at runtime.

代码审查人员看到的是左侧显示的内容：系统提示词 Markdown 文件中的单行更改。

英文原文 What the code reviewer saw is here on the left-hand side. It was a one-line change in the system prompt markdown file.

改动很容易，理解很简单，审批很轻松。但在现实中，该代码修改虽然是局部的，其行为层面的变化却发生在生产环境和运行时。这简简单单的一行，改变了 Agent 的运行机制：它增加了额外的步骤，改变了 Agent 与其他子 Agent 的协作方式，改变了 Agent 调用工具的方式。所有这些可能多达数千种的潜在执行轨迹（trajectories），都不在你的静态代码中，它们只存在于你的可观测性后端，只存在于你的链路追踪（traces）里。因此我们说：diff 告诉你改动了什么，但 trace 告诉你实际发生了什么。这里发生了一个转变，即 trace 正在成为新的事实来源。关于 Agent 实际在做什么的结构化日志，才真正代表了这些系统在运行时的状态。在传统软件中，逻辑被写入代码，在推向生产环境之前很容易确定运行时行为；但现在，逻辑只存在于运行时。当我们看待回归测试时，可观测性就变得必不可少。书写内容与实际发生之间的这一鸿沟，充斥着无声的错误。因此，为了捕捉这些错误，我们需要从审查 trace 开始进行回归测试。

英文原文 Easy change, simple to understand, simple to approve. But in reality, this code change was local, but the behavioral changes of this code change was in production. It was in the runtime. This one simple line has shifted how the agent operates. It's adding additional steps. It's changing how the agent works with other sub-agents. It's changing how the agent calls tools. All of these different trajectories, which could be thousands of possible trajectories, are not in your static code. They're only in your observability back end. They're only in your traces. And so, what we are saying here is that the diff tells you what changed, but the trace tells you what actually happened. And there's a shift here, that traces are becoming the new source of truth. These structured logs of what your agents are actually doing actually is what truly represents what these systems are doing. In traditional software, logic was written down. It was very clear to determine what that runtime was before you ever pushed production. But now the logic only exists at runtime. The observability becomes essential when we're looking at regression testing. This gap between what was written and what actually happens is filled with silent errors. So to capture that, we need to start our regression testing by looking at our traces.

构建五步回归闭环

那么让我们一起构建这个回归闭环。这是一个五步流程：我们将从生产 traces 出发，构建评估项（evals），运行实验，最后将其收敛为 CI 中的自动门禁。首先我将进行五步的高层级概览，然后我们进入实际产品，展示你如何亲自操作。

英文原文 So let's build out this regression loop together. It's a five-step process. We're going to start with our production traces. We're going to build evals, run experiments, and then close it all up to be an automatic gate at CI. First, I'm going to do a five-step high-level overview. And then we're going to go into the actual product and show you how you can do it yourself.

第一步是选择数据集。这听起来很简单：我们要提取真实的生产 traces。既然我们已经拥有真实用户的查询、真实输入和真实工具调用，就不需要合成数据，直接从中拉取即可。重要的一点是，我们的数据集要能够代表用户输入我们系统的平均工作流；但同样重要的是，我们要捕捉已知失败。把常常出错、常常在评估指标上失败的时刻过滤并收录进数据集中。你还需要捕捉边界情况，它们可能不常见，但同等重要。此外，我们经常看到用户遗漏的一点是，捕捉我们想要保护的成功工作流。因为再次强调，我们不仅要确保修复能起效，还要测试我们没有破坏原本正常运转的功能。因此，在数据集中涵盖这全部四项至关重要。拥有了这个生产数据集后，我们就可以构建回归测试套件的其余部分了。

英文原文 So step one is we're going to select a data set. Seems simple enough. We want to pull real production traces. We don't need to synthesize data. If we already have real user queries, real inputs, real tool calls, we're pulling from that directly. It's important that our data set is a representative work is representative of the average workflow that our users are going to be pushing into our systems. But it's also important that we capture known failures. We filter out com moments where often errors, often fails at eval metrics. Capture those into your data data sets. You also want to capture edge cases. Maybe not as common, but just as important. And one thing that we often see users forget is capturing successful workflows that we want to protect. Because again, we're not just trying to make sure that the fix is going to work, but we also want to test that we're not going to break something that was already working. So it's important that we capture all four of these in our data set. Once we have this production data set, we can then build out the rest of our regression testing suite.

第二步是建立评分机制，这就是引入评估器（evaluators）的地方。现场举手示意一下，有多少人熟悉评估 Agent 的概念？很高兴看到这么多双手，这是 Agent 工程的核心基石部分。

英文原文 The second step is we want to have a scoring mechanism. And this is where we bring in evaluators. Now, show of hands, how many here are familiar with the concept of evaluating agents? I'm so happy to see so many hands. This is a core foundational part of agentic engineering.

评估器让我们可以提取对工程师和产品团队至关重要的指标和维度，并将其实际量化。这是什么意思？以一些对 Agent 很重要的指标为例，比如幻觉、准确性、工具调用轨迹、步骤效率。所有这些指标在本质上都是主观的。你可能会让人工来审查它们，并潜在地判断某件事是否存在幻觉、是否采取了最高效的路径。但我们希望能够自动化这一过程，将主观指标转化为数值分数。我们通过利用 LLM 来做到这一点：采用“LLM as a judge”的概念，让 LLM 对 span、trace 或某些日志数据进行判定。LLM 拥有一套特定的指南来判定某件事是幻觉还是事实、是高效还是低效。现在，我们基本上完成了一个二元分类。在右上角这个示例中，你可以看到一个任务完成度评估，其中作为裁判的 LLM 负责判断某件事是完成还是未完成。

英文原文 Evaluators allow us to take metrics and dimensions that are important to your engineers, your product team, and actually quantify them. What do I mean by that? Let's take some metrics that are important for your agents, things like hallucination, accuracy, tool trajectory, step efficiency. All of these metrics are subjective in nature. And you may have a human that reviews them and can potentially determine whether or not something was hallucinated, whether or not the most efficient pathway was taken. But we want to be able to automate this process. We want to turn a subjective metric into a numeric score. And we do this by leveraging LLMs. We use a concept of LM as a judge, where we judge a span, a trace, some log data against an LM. The LM has a particular guide of how it determines whether or not something was hallucinated or factual, something was efficient or not efficient. And now we've done essentially a binary classification. In this example at the top right corner, you could see a task completion eval, where the LM as a judge is has a task of determining whether or not something was complete or incomplete.

现在，我们把一个主观指标基本上转化为了 0、1 的二元分数。你可以将分数映射到 0 到 5，也可以设置多个不同的标签，但你现在已经将一个主观衡量转变为了可以据此评估的定性分数。你不仅限于使用 LLM 裁判，还可以根据具体指标使用基于代码的评估器或基于机器学习模型的评估器。基于代码的评估器非常适合确定性检查，而 LLM 裁判则适合非确定性检查。一旦我们整理出所有关键指标的清单，就针对每一项构建评估器。现在我们就有了一个可供比对的测试套件。

英文原文 Now we've taken a subjective metric and we've essentially turned it into a binary score, 0 1. You can translate the score across 0 to 5. You can have multiple different labels. But you've now turned a quantitative measurement into a qualitative score that you can measure against. You're not limited to LM as a judge, you can also use code-based evals or ML-based evals as well, determine based on what that metric is. A code evaluator is great for your deterministic checks, but an LM as a judge is good for your non-deterministic checks. So, once we have a list of all of our metrics that are important to us, we build evals for each of them. Now, we have a testing suite that we can go against.

第三步是运行基线实验。这个实验的做法是：我们将 Agent 拿来，针对所有生产 traces、所有生产数据集运行。在获得那些生产数据集的输出之后，我们在其之上运行评估测试套件，这就是我们的基线。你可以在 SDK 中做到这一点，只需调用 run experiment，传入数据集、传入任务、传入评估套件，就能获得这些结果。我们稍后会讨论如何在 UI 中实现，以及如何通过编码 Agent 来完成。

英文原文 Step three is we're going to run our baseline experiment. And what this experiment is is we're going to take our agent and run it against all of our production traces, um all of our production data sets. We're after we get the output of those production data production data sets, we're then going to run our eval testing suite on top of that. And that's what's going to be our baseline. Now, you can do this in the SDK, it's just run experiment. You'll pass in that data set, pass in that task, pass in your evaluation suite, and you'll get those results. We're going to touch on how you can do this in the UI, as well as how you can do this with your coding agents.

一旦有了基线实验，你就加入那单项修改：修改策略，重新运行评估，查看评估结果。这是一个简单的流程。现在你可以快速迭代，不仅可以测试单次策略变更，还可以在 Prompt 中测试多种修改，测试多种模型。如果团队跑来对你说：“我们想切换到传说中的新模型，它贵了 5 倍。”在证明能获得良好的投资回报率（ROI）之前，你不会贸然切换。这就是你用一组数值测量来证明切换到更昂贵模型是否真能提升投资回报的方式。你可以调整策略、重跑并对比；重跑并对比更改 Prompt、更改交接（handoffs）、更改工具、更改模型会对整体输出产生怎样的影响——所有这一切都无需部署到生产环境。

英文原文 But, once you have that baseline experiment, you're then going to add your one change. Change that policy, rerun the evaluation, what are the eval results? A simple process. Now that you can quickly iterate on, and not just with one policy change, but test multiple changes within your prompts. Test multiple models. If your team comes with you comes to you and says, "We want to switch the new fable model, it's five times more expensive." You're not going to switch without proving that you're going to get a good ROI. This is how you can prove that with a numeric set of measurements to determine whether or not it actually is improving your investment to switch to a more expensive model. And you can adjust this policy, rerun, and compare. Rerun and compare how changing the prompt, changing handoffs, changing tools, changing models is all going to affect your overall output. All without having to deploy to production.

随后我们可以将其自动化：将此实验推送到 CI 中以完成自动化闭环。现在，每当有 Pull Request 时——比如你在 GitHub Actions 中配置好——每个 PR 都会针对团队认为关键的评估指标运行一遍实验工作流。在满足所列出的所有回归指标之前，不得合并。此时你不再是凭感觉推送，而是满怀信心地推送，确信改动确实对性能产生了积极影响；如果结果是负面的，就退回、测试并再次迭代。

英文原文 And then we can automate this. We push this experiment into CI to complete this automation. Now, each time that you have a pull request, let's say you set this up in GitHub actions, for example, each pull request each PR is run through an experiment workflow against the evaluations that your team has deemed important. And you don't merge until it meets all of the regression criteria that you have listed. Now, you're no longer pushing on vibes, you're pushing with confidence that you actually do have a positive impact on your performance.
