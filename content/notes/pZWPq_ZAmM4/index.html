长程 Agent 架构的三大支柱

在 Lovable 过去的某个阶段，我们曾将 Agent 的运行时长限制在 30 分钟以内，因为当时认为它们无法稳定工作更长时间。但现在我们取消了时长限制，Agent 可以连续运行 10 个小时以上。

接下来我将详细阐述支撑长程运行的底层架构改造。这主要涵盖三个部分：

  1. Agent 运行时本身（Agent Runtime）：如何支持其长时间连续执行；
  2. 计算环境（Computer）：Agent 实际开展工作、启动开发服务器并验证行为的沙箱；
  3. 验证机制（Verification）：若要让 Agent 长时间工作，必须具备健全的反馈闭环，防止其偏离正确方向。
英文原文 And at some point in Lovable's history, we used to limit our agents to work for only 30 minutes because we thought they weren't reliable to to work for a longer amount of time. But now we've changed this to really be without any any sort of bound in terms of the length an agent can work. And so you can imagine agents working for for 10 hours plus.

Um, and so I'll I'll go into some of the things that we've done in our architecture to to enable this. And so the first piece is really around the agent runtime itself and how how we enable that to to run for a longer amount of time. And the second piece is the computer where each of these agents are actually doing their work, running a dev server, and actually verifying what it's doing. And so so the last piece then is the verification itself where if you want an agent to to work for a long amount of time, you need to make sure that you have these feedback loops in place so that it's not kind of going off in in in the wrong direction.

支柱一：Agent 运行时与轨迹日志

首先探讨 Agent 运行时本身。通常有三种不同的信号源会与 Agent 交互：人类用户发起的 Prompt 交互、其他协同 Agent，或是按定时任务唤醒的系统机制。我们的架构设计是：为每个 Agent 维护独立的收件箱（Inbox），所有信号源均向该收件箱发送消息（例如一条询问“当前状态如何”的消息）。

Agent 本身可被视为常驻运行的工作单元。假设它已执行了三个操作：一个请求、一次工具调用以及获得了相应结果，此时便准备好接收消息。由于任何实体都能向收件箱投递消息，Agent 随后会将消息写入自己的“轨迹”（Trajectory）中——本质上就是它的任务历史记录。普遍使用 Agent 的人对这种交互应该并不陌生。

英文原文 Um, and so if we start by looking at the agent runtime itself, you can imagine that you have really three different sources that can interact with an agent. So it can be yourself kind of prompting this or a human. It could be other agents and it could also be just a system on on a schedule waking up. And the way we chose to architect this is that for for each agent we have a separate inbox where any of these sources would kind of send in messages. And so you might have a message here like what's the status. And you can imagine you have this agent and this agent is kind of an always on agent that that might be working, right? And so you can imagine it has done like three actions here, a request, a tool call, and it got some some result. And then at this point the agent is ready to actually receive messages. So since anyone can drop a message into this inbox, the agent then can copy that itself into its own what we call a trajectory. Basically it's a task history. And this is the type of interaction that I think you're familiar with if if you're using agents overall.

这是该运行时的第一个设计原则。接下来再介绍几项特性。

Agent 运作所依赖的“轨迹”，记录了截至目前发生的所有事情，是其所有记忆能力的基石。我们在设计该轨迹时深度参考了 Git 的理念。具体而言，该轨迹是一个仅追加日志（Append-only Log），其中每个事件都指向其父节点（即前一个事件）。

得益于这种结构，它获得了与 Git 类似的分叉能力（Fork）：两个独立事件可以指向同一个父节点，从而形成分叉。这意味着我们可以在历史记录的任意时间点启动并行 Agent，而无需复制底层的共享历史。从语义上看，合并这些分支的效果并不明确，因此与 Git 不同，我们并不合并 Agent 轨迹，但可以将其分叉派生出来，让各 Agent 彼此协同通信。

Um and we designed this trajectory with really Git as inspiration. And so the trajectory, what is it? It's an append-only log where each event points towards a parent, the previous event. Um and because of this, you get a nice capability just like in Git where you can fork things, right? So you can have two events pointing to the same parent, which essentially creates a fork. Um and because of that, you can kind of spin up parallel agents at at any point of time in the history without having to duplicate all of the kind of the shared history. And these agents can can talk to each other.

另一项设计关键在于：该轨迹忠实记录了 Agent 发生的一切完整历史，包括每一次工具调用、平台上的各类事件、调用成功或失败的状态等；其中不少信息可能并不适合直接放入 Prompt 中。

基于这一仅追加日志，我们再按需提取并构建实际输入给 LLM 的 Prompt。为什么要把两者分离？原因之一在于：面对冗长的历史上下文，通常需要对早期步骤进行某种程度的压缩或摘要。但摘要策略因模型而异——面对不同上下文窗口长度的模型，需要采取不同的摘要时机与方案。将 Prompt 的组装与实际任务历史完全解耦后，我们便能够针对任意模型和任意任务类型，动态渲染出最适配、最优化的 Prompt。

英文原文 Um the other thing that we made sure to design for is that this agent trajectory, it includes kind of the full history and everything that happens with the agent. Well, one one reason is that when you build a prompt, you if you have a long history, you probably want to do some sort of compaction and you want to summarize part of that history in in the earlier steps, for example. But this summarization would differ. For example, if you use different models with different context lengths, you would probably think differently about when you should summarize and not. And so by separating the the prompt from the actual task history, we're able to render prompts for for any type of model or or any type of task that that we can kind of find the best and optimal prompt for.

为什么需要做到进程无状态？因为在 Lovable，我们每天向这套系统部署 700 次，大约每两分钟部署一次。设想一个 Agent 正在为客户持续运行 10 个小时，你既不能打断它的工作，又必须确保它能运行在最新的部署版本上——这可能是为了引入新功能，也可能是为了紧急修复 Linux 内核的安全漏洞。

由于任务历史与执行进程完全解耦，单一 Agent 在执行特定任务时，后台接管并提供算力的进程可以随时无缝轮换。即使任务持续运行 10 小时甚至更久，底层部署能够持续迭代更新而不产生中断。

英文原文 And and then the question is why why do we care about this? Well, at Labbable this system we deploy to it 700 times per day. So that's about once every two minutes. And you can imagine if you have a agent working for for 10 hours, you want to not disrupt that agent when it's working, right? This this agent is doing something for for a customer. But at the same time we want to make sure that this agent is running on the latest deploy. 支柱二：计算沙箱、快照与 Rust 化开发服务器

接下来介绍平台的第二块核心：计算环境（Computer）。这是 Agent 实际开展工作的环境。在探索为 Agent 提供工作沙箱的过程中，我们经历了大量的迭代并测试了众多供应商方案，最终落地了当前重点研发的系统——计算环境快照机制（Checkpointing）。

当用户创建一个新项目时，系统会基于一个通用的“黄金快照”（Golden Checkpoint）进行初始化。它包含预装的操作系统、系统服务、常用开发工具以及就绪的开发服务器。该快照涵盖磁盘状态、内存数据以及运行中的进程。创建新项目时可直接获得这套环境，整体拷贝耗时仅约 230 毫秒。
