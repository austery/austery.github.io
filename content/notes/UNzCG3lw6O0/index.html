开场与“skill hell”

大家好。我本来非常希望能来参加 AI Engineer World's Fair，但家里有事，我没能到场。不过，我不会让你们空手而归。我要把原本打算在旧金山做的演讲讲给你们听。这场演讲叫《缺失的手册：如何写出优秀的 skill》。我认为，分辨好 skill 与坏 skill 的能力只会越来越重要。作为开发者，我们似乎很擅长给自己找各种各样的“地狱”。几年前我们有教程地狱：你一头扎进一大堆教程想学点东西，却无法把它们拼起来，陷入一个出不来的循环。我们还有框架地狱：每隔十分钟就有一个 JavaScript 框架发布，你得一直学最新最热的东西。现在我认为我们又有了另一种地狱，就是 skill 地狱。skill 地狱是指：有大量 skill 可以自由获取，你可以下载、贡献、自己摸索，但你并不真正知道这些部分如何协同工作。你分不清好 skill 和坏 skill。这意味着人们试图把这些框架拼凑起来，试图一次性尝试市面上的所有东西。他们没法，或者说他们得不到这些 skill 自己所承诺的结果。这在个人层面是如此，在组织层面也是如此。组织不知道、也不理解如何构建好的 skill，如何把自己的操作流程变成 agent 能做的事。如果不这么做，就很难获得 skill 能带来的丰厚回报。“再来一个 skill 就好，兄弟。”我们似乎就是这么说的。我也有些内疚，因为我有 Matt PCO skills，也就是我的 skills 仓库，它是最受欢迎的工程类 skill 集之一。所以我想帮助使用我 skill 的人走出 skill 地狱。

技巧一：决定 skill 由用户调用还是模型调用

所以这就是第一条技巧：决定你的 skill 是由用户调用还是由模型调用。你可能会觉得模型调用的 skill 更好，对吧？因为模型可以自己调用，用户也可以调用，更灵活。但每当你往 agent 的环境里加一个模型调用的 skill，就会增加我所说的 agent 的上下文负载：它添加了一条新的描述，这在每次请求上都会消耗你的 token，同时也给 agent 增加了另一件需要思考的事。所以如果你有 100 个模型调用的 skill，agent 的上下文里就会有 100 条描述。因此，要么压低模型调用 skill 的数量，要么干脆全用用户调用的 skill，似乎都说得通。但用户调用的 skill 有另一种负载：你拥有的用户调用 skill 越多，用户的认知负载就越高。换句话说，用户需要记在脑子里的东西越多，对驾驶员的技能要求就越高。所以如果把 Matt Pot skills 和 superpowers 比较，superpowers 主要是模型调用的 skill，给 agent 以超能力。而我的 skills，我更喜欢完全掌控。这意味着我能让 agent 的上下文负载尽可能小，但它确实给我自己增加了更多认知负载。所以我需要非常深入地理解这些 skill，才能最大限度地用好它们。那我为什么这么做？为什么我偏好用户调用的 skill？每当你有一个模型调用的 skill，基本上你就要付出不可预测性的代价，因为每当有一个上下文指针从一个资源指向另一个资源，模型可能就是选择不去跟随它。即使它对任务来说绝对完美，它也可能就是选择不调用这个 skill。我更愿意去掉这一层不可预测性，给用户多增加一点认知负载。这样得到的结果是，你把一整类问题直接去掉了，让它根本不再成为问题，因为这种不可预测性会让人需要去评测自己的 skill，确保它们在正确的时间被调用，这真的很讨厌，是我更愿意避免的问题。但我希望在这里向你展示的是，模型调用的 skill 和用户调用的 skill 各有同样的代价，所以选哪一种不是一个轻松的决定。这就是触发，即 skill 如何被调用。

二、结构：步骤与参考

现在来谈结构，也就是 skill 的内部布局。我认为大多数 skill 里需要放入两个主要单元：步骤和参考。步骤是 skill 要逐步走完的流程，参考是帮助它走完这些步骤的任何辅助信息。你可以有没有步骤、只有参考的 skill，也可以有没有参考、只有一组简单步骤要走的 skill。但如果你开始把 skill 看作由这两个单元组成，会大大帮助你把它们拆解开来。看一个例子：我的一个 skill 叫 two PRD，它根据当前的上下文窗口创建产品需求文档。它有三个步骤：找到相关上下文；与用户确认 test seam，这里有一个小小的人在回路检查点，只是为了确保我们在测试上没做什么奇怪的事，我觉得这非常重要；然后撰写产品需求文档，以此完成这三个步骤。它有两份参考材料：一点关于什么是 test seam 的参考，以及一个产品需求文档模板，就是一个字面意义上的 markdown 模板，用来撰写 PRD。所以这是从零开始写 skill 的好办法：你先判断是否需要一些步骤，然后写这些步骤，再判断这些步骤需要什么参考材料，把它放进 skill 里专门存放参考材料的另一个小位置。

The steps are the step-by-step procedure that the skill is going to walk through. And the reference is any supporting information that helps it walk through those steps. You can have skills that have no steps and are only reference. And you can have skills that are no reference and only a set of simple steps to walk through. You work out if you need some steps. Then you write those steps and you work out what reference material those steps need and you put it in a separate little spot in the skill which is for reference material.

技巧三：让主 skill.md 尽可能小

不过，有一个非常重要的约束需要考虑，也就是第三条技巧：我们要让主 skill.md 文件尽可能小。每个 skill 由描述、skill.md 文件，以及从它分出去的任何参考材料组成。如果我们把这个 skill.md 文件做小，就能在很多方面节省。更小的 skill 更易维护、更易审查，需要思考的词更少。而且你每删掉一个词，就是省下一个 token，这会成倍地降低你的 skill 的成本。所以我确实认为，小 skill 对维护者和用户都非常重要。让 skill 变小的一个很有用的办法，是思考 skill 的不同分支，即 skill 可以被使用的不同方式。因为如果有参考材料只在某一个分支里用到，那它就是可以从主 skill.md 里移出去的候选。比如看我这个 two PRD，有两份参考材料：什么是 test seam，和 PRD 模板。PRD 模板我们每一次都需要，因为我们总是在创建 PRD。而什么是 test seam 的信息大概也每次都需要，因为我们总是会询问 test seam。所以 two PRD 只有一个分支，所有参考材料都属于这个分支，因此大概也应该放在 skill.md 文件里。但如果看我的另一个 skill，domain modeling，它做两件事：更新一个叫 context.md 的本地词汇表，并创建架构决策记录。换句话说，它在做两件不同的事。或者它也可能选择两样都不做，那样它既不需要那个模板，也不需要 ADR 模板。所以，domain modeling 有两个或者也许三个分支。这意味着我们不需要把 ADR 模板或 context.md 模板放进主 skill 里，它们可以被移到单独的区域。做法是：有 skill.md 文件，然后把它放在一个上下文指针后面，让上下文模板指向 skills 文件夹里一个单独的 markdown 文件。那个上下文指针字面上就是说：如果你需要这个模板，或者需要更新 context.md 文件，就去这个文件。我把它称为外部引用。它是在 skill.md 之外的引用，你可以很容易地引用它，agent 也可以很容易地拉取进来，因为它是和 skill 打包在一起的。所以这是让 skill.md 尽可能小的一种技术，而这有很多好处：把分支性的参考材料藏在上下文指针后面。换句话说，如果你觉得你的 skill 会以很多不同方式被使用，就把与这些分支相关的参考材料藏到上下文指针后面。这就是结构：我们要考虑让 skill.md 超级小；要考虑 skill 里的分支，把材料移到上下文指针后面；还要考虑步骤和参考，它们是 skill 里的两个主要单元。

三、引导：引导词与步骤内的工作量

接下来是引导，也就是我们让 agent 去做我们想让它做的事的实际办法。对我来说，引导归结为一个非常酷的技巧，也是我最希望你们从这次演讲中带走的主要东西。这个技巧解决的问题是：agent 不做我想要的事。换句话说，我在 skill 里指定了某件事，我以为自己已经说得很清楚，然后它就是不去做。我认为发生这种情况的主要原因，是你没有使用一种叫“引导词”（leading words）的技巧。引导词，或者如果你喜欢文学理论的话，我想可以叫 leitmotif，这个想法是：有些词能把大量含义压缩进很小的空间。这些引导词对 agent 非常有力，因为你把引导词放进 skill 本身的文本里，然后 agent 会把这个引导词重复给它自己，作为它运行的一部分、它思考 token 的一部分，也作为它给你的输出的一部分。因为它在重新强调这个词，而这个词有望描述你想从 agent 那里得到的东西，这就会改变它的行为。让我们用一个例子把它具体化。假设我们有一个 agent 的经典问题：它们逐层编码。也就是说，如果你给它们一大块工作，它们通常会先写完所有的数据库层，然后是所有的 schema，然后是所有的 API 端点，然后是所有的前端。它们不会做那种典型的人类做法：尽早寻求反馈，先让一个小东西跑起来，再从那里扩展出去。现在，我们可以试着鼓励 agent 这样做，只需说：别逐层编码，确保先创建一个小切片，然后从那里继续。但如果我们改用一个引导词呢？我们说 vertical slice（垂直切片）就是我们的引导词。我们想把工作切成垂直切片，而不是水平切片。垂直切片在开发中是一个相当众所周知的术语，所以这有望触发 agent 的先验，它就会理解我们的意思。我们不必弄成一个只有“垂直切片”两个词的 skill。我们做的是把很多含义压缩进一个相对简短的短语，然后在整个 skill 中重复它。这个技巧的酷之处在于你可以知道它是否奏效：你在 skill 里说 vertical slice，然后你会在推理轨迹里注意到它说：“好，我们要把这件事做成一个薄的垂直切片。”那么你应该会得到更好的实现计划。我向每个人解释这个技巧时，他们都有点觉得：“哦对，我早就在这么做了，我一直在用这些小短语去鼓励 agent 做我想要的事。”我现在要求你们的只是：在 skill 里一致地使用它们，并观察思考轨迹，看 agent 如何采纳你的做法。所以，如果 agent 没有做你想要的事，你往往需要让你的引导词更一致、更有力，并去寻找其他的引导词，因为英语就像一个很宽的 API，有许多不同的函数可以调用、许多不同的东西可以实验，有很多引导词候选，而 agent 其实很擅长帮你想出它们。你可以对 agent 使用的另一个小杠杆是：有时 agent 就是没有做足功夫（leg work）。我的意思是，比如我们在某一步，也许这一步是提出澄清问题，或者探索代码库，而 agent 就是做得不够。它没有在那个特定步骤上投入足够的精力。一个真正经典的例子，也是我几乎在所有存在它的地方都发现过的，就是 plan mode。因为在 plan mode 里有两个步骤：提出澄清问题，然后创建计划。我在尝试过的每一种 plan mode 实现中都发现，“提出澄清问题”就是从来没有做足功夫。它看到自己的最终目标是创建一个计划，所以它只在“提出澄清问题”上做一点点功夫，问你几件事，然后迫不及待地创建计划。那我的解决办法是什么？我不用 plan mode，而是有一个叫 grill with docs 的 skill，它算是我的“提出澄清问题”阶段。然后我把它拆成一个单独的 skill，也就是把规划拆成它自己的 skill。所以 grill with docs 现在是它自己的 skill，agent 只能看到流程中的那一部分。grill with docs 完成之后，我们再去做 two PRD。换句话说，有第一步和第二步，但 agent 每次只看到一步。所以这是一个很酷的技巧：通过隐藏未来的目标、隐藏后续步骤，来增加你当前所处步骤的工作量。并不总是需要把 skill 拆成单独的步骤，但在你特别想要额外一大块工作量的情况下，真的没有哪种技巧能比得上它，效果非常非常好。这就是引导：用引导词把你想要的东西捕获在小而可复用的 token 里，然后确保每一步做的工作量合适。

四、精简：失败模式

下面进入精简。精简其实就是一组快速罗列的失败模式，也就是你可能搞错的不同事情。第一点相当明显：我们不想要庞大的 skill。庞大的 skill 通常是其他问题的某种症状，也就是其他这些失败模式之一的症状。第一个很简单：不要重复自己。你需要留意重复。总的来说，我喜欢让 skill 的每一部分都有单一事实来源。换句话说，如果你有一份参考材料，比如 PRD 模板，或者更小的东西，比如什么是 test seam，你要确保不要在多个地方重复它，或者在多个地方涵盖多个步骤。只要确保每一部分都有单一事实来源，而且即使跨参考材料也不要重复自己。skill 变大的下一种方式是沉积物（sediment）。沉积物是人们共同处理同一组文档时的经典现象：每个人都开始往一个共享的 markdown 文件里贡献内容，人们加入自己的东西，却没有勇气删除和修改别人的。于是你最终得到大量沉积物，往往是与这个 skill 无关的材料，尤其是那些没有被妥善安排的内容。对于有大量沉积物的 skill，你真的需要看结构，这是你要做的第一件事。你要确保被添加的内容对所有分支都相关。如果不是，就把它移到正确的分支里；或者如果它完全无关，也许就直接移除或干掉它。或者里面有些东西完全过时了，那你就需要把它彻底干掉。下一种失败模式在 agent 帮你写 skill 时非常常见，就是 noop：skill 里那些看起来在做什么、但在这个 skill 的上下文中实际上并不影响 agent 行为的东西。假设我们有一个 implement skill，其中有整整一段告诉 agent 写一条冗长详细的提交信息。如果你把那一段删掉会怎样？agent 大概仍然会写出一条像样的、挺长的提交信息。人们经常问我，我怎么把我的 skill 做得这么小，其实就是用这些技巧：用删除测试，确保把东西压缩成引导词，里面没有任何无关的东西，也没有任何沉积物。
