These tokens can add up really really fast. Very quietly they got very expensive.

英文原文 The second thing that will go wrong is they will wreck your code base because typically the way the review agents work is they'll leave comments on GitHub and your coding agent picks them up and resolves them. 英文原文 The next thing that go wrong is that every time you run a review agent on the same pull request, you will somehow find new bugs in the sense that it will keep catching new things in the pull request very annoyingly, and you will And like I said, bugs will appear to be fractally infinite.

优化方向一：优化提示词与规避细枝末节

因此，你要做的第一件事，也就是最立竿见影的低垂果实，就是优化提示词。你一开始用的是非常简单的提示词，比如“审查此 PR 并按 GitHub API 模式格式输出评论”。一般来说，围绕 Bug 有两个主题：寻找特定类型的 Bug，以及第二点，跳过琐碎的挑刺。这就是你的提示词需要重点围绕的方向。你需要明确指定具体的 Bug 类型，你可以针对代码库中过去发生过的宕机和事故做一些内部数据分析，找出你们最容易产生哪些类型的 Bug，建立一个分类目录，然后让提示词去寻找那些特定类型的 Bug。

英文原文 So, the first thing that you want to do, the lowest hanging fruit, what is you want to optimize the prompt. You started with a very simple prompt, something like review this PR and then output the comments in GitHub's API schema format. Generally, there's two themes within the bugs. Look for specific bug types, and second, skip the nitpicks. And that's what you want to orient your prompt around. You'll want to ask for specific bug types, and you can kind of do some internal data science on existing outages and incidents that have happened in your code base and figure out what types of bugs you have the highest propensity to produce. Create a catalog of them, and then have your prompt look for those specific bug types.

第二点是，你必须明确告知它什么是琐碎挑刺（nitpick），并要求不要去寻找它们。挑刺可以是任何琐事，比如质疑为什么在某个特定地方没有加三层防御，或者为什么错误处理写得略显粗糙。

英文原文 The second is you'll need to expressly tell it what a nitpick is and not to look for them. And nitpicks can be anything from asking why there isn't three layers of defense on this particular thing, or why error handling is done in this slightly shoddy way.

当你修改这些提示词时会遇到的情况是，仅仅修改提示词中很小的一点，就会对 Agent 在 PR 上编写的评论数量产生异乎寻常的巨大影响。这相当吓人，因为这意味着你根本不知道它是否遗漏了 Bug，你不知道反事实情况（counterfactual）。

英文原文 Now, the thing that you'll run into when you change these prompts is when you change a small thing in the prompt, it'll have a weirdly big impact on the number of comments that your agent is writing on your pull request. This is quite scary because it means you don't really know if it's missing a bug or not. You don't know the counterfactual.

验证 Agent，或者实际上任何审查者或测试工具，都能够告诉你 Bug 的存在，但遗憾的是无法证明 Bug 的不存在。这在某种程度上是该模式的局限性。而使这一问题尤为棘手的，是那些极其罕见且日益稀少的 Bug。事实上，根据我们掌握的数据分析，大约每一千个 PR 中才会出现一个通常意义上的灾难性 Bug，或者说每一千行代码中可能才有一个灾难性 Bug。

英文原文 The validation agents, or really any reviewer or tester, can can tell you about the presence of bugs, but it fortunately can't tell you about the absence of bugs. That's that's sort of a a limitation of the format. And what makes this particularly difficult are bugs that are extraordinarily rare and getting rarer by the day. In fact, according to our data science, only about one out of every thousand pull requests has a generally catastrophic bug in it. Or maybe one out of every thousand lines of code has a catastrophic bug in it.

正因这类 Bug 非常罕见，你可能发布了一个自认为非常优秀的 Agent 版本，但它却暗中漏掉了 PR 里的灾难性 Bug，而你很长时间都不会察觉，因为你们本就不常产生那种 Bug。

英文原文 And so, because these bugs are very rare, you might release a version of your agent that you think is very good, but it secretly misses a catastrophic bug in a pull request, and you wouldn't know for a long time because you don't produce those bugs very often.

优化方向二：构建历史 PR 数据集与持续更新

这就引出了第二项改进：你需要一个历史 PR 数据集。如果你们公司习惯良好、每次代码库出现问题都会详细记录归档，那做起来相对容易。如果具备这一点，你就会有一份以往导致过宕机和事故的 PR 列表。你需要对它们进行编目，然后基本上让审查 Agent 的各个版本都在这些 PR 上跑一遍，看看它能以多高的频率捕获这些 Bug。

英文原文 And so that brings us to the second improvement. You will want a data set of historical PRs. This is relatively easy if you're one of those companies that very nicely catalogs every time something goes wrong in your code base. If you have that, then you'll have a list of pull requests that have caused outages and incidents in the past. You'll want to catalog them and then essentially have any version of your review agent run through those and see with what frequency it can catch those bugs.

这能让你更有底气地去微调提示词。但与此同时，Bug 的有趣之处在于，在不断变化的世界中，Bug 的拓扑结构和本体结构是随时间演变的。因此你需要一个实时更新的数据集。这非常棘手，因为除非你拥有数以百万计的 PR，否则实际上很难在 Bug 类型上获得相当高的覆盖率。诚然，大约 80% 到 90% 的 Bug 只是过去错误的重蹈覆辙，但随着 Coding Agent 越来越强，它们会开始犯下全新的错误。它们会以我们此前未曾预料到的全新方式失效。

英文原文 Now, this will allow you to tune the prompt a little bit more confidently. But at the same time, the interesting thing about bugs is in a changing world, the topology and ontology of bugs changes over time. And so you'll need to have a real-time updating data set. And this is tricky because unless you have millions and millions of pull requests, it's actually hard to have reasonably high coverage of bug types. It's true that about 80 or 90% of your bugs will be just repeats of prior mistakes, but increasingly as code agents get good, they're going to start making novel mistakes. They'll fail in new ways that we've not anticipated before.

而这正是你开始遭遇局限的地方。顺便插一句，这正是我们在 Griptile 所做的事情，不同之处在于我们实际拥有来自众多不同公司的大量代码，可以在极大规模的 PR 语料库上进行测试，因此能够非常自信地改进我们的 Agent。这也是为什么我们能够在边际上榨取少量性能优势，而内部自研审查 Agent 却做不到的原因之一。不过，特别是针对你所在公司的特定场景，利用内部数据做到这一步也能走得相当远了。

英文原文 And so this is where you will start to hit limitations. Now, quick side note, this is kind of what we do at Reptile, except we actually have a lot of code from a lot of different companies and we can test across a very, very large corpus of pull requests and therefore improve our agent very confidently. It's one of the reasons why we're able to eke out little bits of performance on the margins in ways that internal review agents can't. But you can get decently far, especially for your particular company, to do this with your internal data.

优化方向三：模型反转策略（Model Inversion）

接下来要做的是模型反转（Model Inversion）。如果在座有人参加了我今年早些时候在旧金山 AI Engineer 大会上的演讲，我当时详细讨论了 Coding Agent 失效的各种方式。通过那项研究，我发现了一个有趣的规律：Claude 模型或 Codex 模型所产生的 Bug 类型彼此之间其实大不相同，在许多方面都存在差异。

英文原文 The next thing you want to do is model inversion. So, for in case anyone was at my talk earlier this year in San Francisco at AI Engineer, I talked a lot about the ways in which coding agents fail. And I discovered an interesting pattern through that research, which is that the types of bugs produced by Claude models or Codex models are actually quite different from each other. And they're different in a number of ways.

举个例子，Claude 模型产生差一错误（off-by-one errors）的概率大约是 GPT 模型的三倍；而另一方面，GPT 模型出现身份鉴权绕过（auth bypasses）的可能性要明显高于 Claude 模型。据我所知，这些完全只是后训练（post-training）带来的副产物。

英文原文 As an example, Claude models are something like three times more likely to produce one-off errors than GPT models. GPT models, on the other hand, are significantly more likely to produce auth bypasses than Claude models. And these are all just artifacts of the post-training, as far as I understand.

为了防止这种情况，你会发现如果用相同的模型去审查由该模型编写的代码，捕获到的 Bug 实际上会相对较少，因为它们在审查时的失效模式与生成代码时如出一辙。因此你需要将模型反转：如果你用 Claude Code 编写了代码，就要使用 GPT 模型来审查；以此类推。

英文原文 Now, to prevent this, you'll find that if you're using the same model to review the code written by the same model, um you'll actually have relatively fewer bugs caught because they fail in the same ways during review that they do during code generation. 优化方向四：深层代码库上下文与活维基（Living Wiki）

第三项改进是代码库上下文。这是我非常关心的事情。在我们做代码验证之前，我们就在做代码库上下文。我们当时试图寻找在超大代码库上进行 RAG 的更好方法。甚至直到今天，人们还认为 grep 实际上已经解决了代码库上下文的所有问题。我个人认为这并不符合事实，原因有二：第一，grep 极其不精准；第二，它非常昂贵。

英文原文 The third improvement is code base context. Now, this is something that I care a lot about. Before we were doing code validation, we were doing code base context. Uh we were trying to figure out better ways to do rag over very large code bases. And even today, people consider grep to effectively solved all of code base context. I actually think that's not true for a number of reasons. One, grep is extremely imprecise. And second, it's very expensive.

给大家一个数量级概念：去年 GDP 增长中有几个百分点来自于推理；而在推理中，非常大的一部分比例来自 Coding Agent。如果你去观察 Coding Agent 的执行追踪轨迹，会发现 Coding Agent 消耗的大部分 Token 全是一回事：grep、读文件、将文件内容写入缓存。这意味着 GDP 增长中有相当大的一部分比例就是“grep、读文件、写缓存”。这非常糟糕。

英文原文 To give you some sense of scale, single-digit percentage points of GDP growth last year were inference. A very large percentage of inference was coding agents. And if you actually look at a coding agent trace, the vast majority of tokens used by coding agents are all the same. grep, file read, cache write for the file contents. That means a non-trivial percentage of GDP growth is grep, file read, cache write. That's very bad.

这是因为 grep 极其不精准，它会读取巨量的文件；我不知道，按 Token 收费的公司或许存在某种不良动机去变着法子多烧 Token。但即便如此，你会发现必须采用更精准的手术式方法来确定应该读取何处。我们的做法是构建一个内部知识库：我们基本上会检查整个代码库的所有不同组成部分，对它们进行编目和索引，标明：“好，这里是鉴权模块。它的工作机制是这样的，数据流是这样的，这是流程图，这是所涉及的每一个文件。”

英文原文 And this is because grep is very imprecise. It's reading files in very large quantities, and I don't know, there's perhaps some adverse incentives for companies paid by the token to figure out ways to burn more tokens. But even so, you'll find that you'll need to use slightly more surgical methods of figuring out where you should be reading. And the way we do this is we produce an internal knowledge base where we essentially check across the entire code base all the different parts, catalog them, and then index saying, "Okay, well, this is authentication. Here's how it works. Here are the flows. Here's a diagram of the flows. Here's every file that's involved."

代码库上下文之所以至关重要，举个例子，比如当你试图捕获鉴权绕过缺陷时：要查明是否存在鉴权绕过实际上非常困难，因为你需要非常明确地了解当你处于代码库该特定区域时，当前究竟是否处于已鉴权的环境中。这非常棘手。因此你会发现必须拥有某种代码库上下文才能胜任这项工作。

英文原文 One example of where code base context matters is, for instance, when you're trying to catch an off bypass. It's actually very difficult to figure out if an off bypass has occurred because you need to have a pretty concrete understanding of whether you're in an authenticated environment when you're in that part of the code base or not. And that's very tricky. And so, you'll find that you will need some type of uh of sort of code base context to be able to do this.

英文原文 Now, one of the ways in which we fight this is by giving agents increasingly more context. 英文原文 Now, the way that Reptile approaches this problem is we actually disintermediate all of these context sources with a living wiki.
