摘要:

Indeed 工程师 Dustin Mihalik 分享了在构建 MCP 应用程序时的实战经验。核心设计原则是将数据检索与 UI 渲染解耦：工具应向大语言模型提供结构化数据以便推理与过滤，同时通过独立的渲染工具向用户展示交互界面，实现模型与 UI 的双向同步。

背景与 MCP 生态实践

大家好，我是来自 Indeed 的 Dustin Mihalik。作为全球领先的招聘平台，Indeed 致力于为求职者打造高效的求职工具。我在公司的 AI 平台团队（AI Platform Team）工作，主要负责 AI 安全防护机制、网关路由以及合规审计等基础设施。在与各大生态伙伴的合作中，我们团队探索了许多前沿项目，其中就包括 模型上下文协议（Model Context Protocol: Anthropic 推出的用于连接 AI 模型与外部数据工具的开放标准，简称 MCP）及其连接器的开发与落地。

在实际构建面向 Claude、ChatGPT 以及我们内部求职助手 Career Scout 的 MCP 应用程序过程中，我们积累了宝贵的实战经验。目前的 AI 交互多数基于对话界面，以职位搜索为例：如果用户询问“奥斯汀的咖啡师职位”，早期的纯文本响应虽然能列出职位，但缺乏品牌展示与交互深度。然而，直接强行注入网页链接往往体验糟糕，甚至被宿主环境限制。因此，如何在 MCP 架构下平衡模型推理、宿主控制与富交互 UI，成为了核心挑战。

解耦黑盒：数据与 UI 必须对等透明

构建高质量 MCP 应用的第一条铁律是：呈现给用户的界面内容，必须同样作为结构化数据交付给模型。

许多开发者在构建 MCP 时容易走入误区——仅仅在前端调用 API 渲染一个漂亮的 HTML 页面或组件，却将该组件视为“黑盒”，模型对此完全一无所知。当用户进一步追问“详细说说第一个搜索结果”或“评估一下这些公司”时，模型由于看不到 UI 里的数据而无法回答，导致体验断层。因此，在基于 MCP 规范设计时，工具返回必须同时兼顾文本/结构化数据（供模型理解）与界面渲染资源（供宿主呈现），确保模型与用户视图保持严格同步。同时，在工具的提示词（Description）中明确标明“结果已在界面组件中展示”，能有效避免模型重复生成冗余文本。

上下文动态同步与状态传递

在支持富交互的应用场景中，第二个关键架构点是用户交互状态的双向传递与上下文同步。

当用户在界面组件中执行操作（如点击“查看详情”弹窗、筛选卡片、或在电商场景中将商品加入购物车）时，这些在客户端发生的行为对于远端的大模型而言默认是不可见的。如果用户接着询问“帮我针对这个职位写一封求职信”，模型若缺失选中的具体职位上下文就会报错或产生幻觉。为了解决这一问题，MCP 客户端架构中提供了类似 updateModelContext 的状态通知机制，每当用户与 UI 交互产生关键动作时，系统需将状态变更作为行上下文（Row Context）同步回模型的会话环境中，使模型能随时感知用户正在查看的具体内容。

数据处理与界面渲染的分离设计

第三条最核心的原则在于：将底层数据检索/处理与前端界面渲染彻底解耦（Separation of Data from UI Rendering）。

这种架构理念同样体现在 OpenAI Apps SDK 等先进规范中。如果一个工具既做数据检索又强行绑定固定的展示组件，模型就失去了灵活编排与深层推理的能力。在标准架构中，应当设计两类工具：

  1. 纯数据检索工具（Data MCP Tools）：负责执行灵活的搜索与过滤。模型可以自主发起多次调用、交叉比对上百条职位数据，并根据用户个性化偏好进行精准筛选。
  2. 轻量渲染工具（Rendering Tools）：仅接收由模型筛选后的实体 ID 列表（如 5 个精选职位 ID），并负责渲染展示组件。

这种职责分离赋予了大语言模型充分的“推理与创造空间”——模型不仅能选择最优结果展示，还能在输出中生成专属的推荐理由或分析文本。将单体大工具拆解为多个小型、模块化的工具，既能防止模型上下文载荷过重，又能让用户同时获得深度的 AI 分析能力与流畅的现代 UI 体验。
