摘要

Anthropic 的最新研究表明，在共享资源场景下，多 agent 团队的表现不如使用一个协调者模式的单一 agent。研究发现，团队规模越大，'摸鱼'的 agent 比例越高，且不同模型的 agent 在行为上存在差异。在信息不完整的情况下，多 agent 协作会导致信息编造，这暴露了现有 AI 评测只关注结果而忽略过程的盲区。研究指出，解决多 agent 协作失败需要根据不同环境采取不同的修复方案，例如在 API key 环境中增加团队领导 agent，在点餐环境中则需要平台级防护。

你给 Claude 一个任务，我也给 Claude 一个任务，我们的两个 Claude 在同一个代码仓库里同时干活。

听起来很美好，对吧？效率翻倍，各干各的。

Anthropic 的最新研究告诉你：这样做，团队的整体表现会比只用一个 Claude 差得多。

意思是：在共享资源的场景里，每人一个 agent 各自为战，结果比大家共用一个 agent 更差。

多 agent 合作的前提本来是"人多力量大"，但实验数据说的是"人多添乱"。

一个 agent 服务所有人，为什么反而更好

Anthropic 的研究团队设计了四个贴近现实的场景来测试这件事：

API 算力预算：一群研究员共享有限的 token 额度，每人有截止日期不同、重要性不同的任务

诊所日程表：多个急诊患者抢同一套时间槽

团体点餐/订票：每人让自己的 AI 助手参与一个共同的订单

合并队列：多个开发者的代码需要在发布截止前通过合并

这四个场景有一个共同特点：资源有限，必须协商。这恰恰是现实工作中最常见的状况。

研究者把 agent 分成几种编队来对比。最关键的两种是：

协调者模式（coordinator）：一个 agent 同时服务所有用户

点对点团队（peer-to-peer team）：每人一个 agent，agent 之间可以互相通信

结果呢？

在全部四个环境中，对 Claude Opus 5 和 Claude Sonnet 5 来说，协调者模式都赢了。

差距从 10 到 45 个百分点不等。

这张图值得细看。

API key 环境差距最大，Opus 5 的协调者达到最优方案的 64%，团队只有 30%；

Sonnet 5 的协调者 32%，团队只有 12%。

为什么会这样？答案藏在 agent 的具体行为里。

团队越大，摸鱼的 agent 越多

API key 环境的核心挑战是：算力不够所有人用，agent 必须主动取消低价值任务，把资源让给高价值的。

团队 agent 最大的问题是：行动太少，反应太慢。

很多 agent 从头到尾什么都没干。而且团队规模越大，"摸鱼"的比例越高。

16 个 Sonnet 5 agent 组成的团队里，只有 10% 的 agent 会采取任何行动。 90% 的 agent 就这么干看着，等资源耗尽。

这跟人类组织里的"旁观者效应"惊人地相似。心理学早就发现，围观者越多，每个人出手帮忙的概率越低。AI agent 也学会了这一招。

更有意思的是不同模型的"性格差异"。

GPT 和 Qwen 的 agent 会频繁地未经同意就取消其他用户的任务，每个回合 3.9 到 7.1 次。

Sonnet 5 偶尔这么干（0.59 次），而 Opus 5 从来不会。

这里面有个悖论：那些"越权"的 agent，团队得分反而更高。因为取消低价值任务本来就是这个环境需要做的事。但评分体系只看结果，不看过程。

它不会告诉你：某个用户的工作被别人的 agent 单方面终止了，而这个用户完全不知情。

这恰恰暴露了现有 AI 评测的盲区：只看"结果好不好"，不看"过程对不对"。

Opus 5 还有一个特别的表现：它在用户之间分配结果最均匀（Jain 指数 0.59），明显高于其他模型。

换句话说，Opus 5 更"公平"，哪怕这意味着总分不是最高的。

你的 AI 助手在替你下单时，编了一些关于你的谎

点餐/订票场景揭示了一个更微妙的问题。

每个用户让自己的 agent 参与一个共同订单。

其中有一个用户会提出一个特殊需求（论文里叫"the ask"），比如一个乳糜泻患者要求两份无麸质配菜来替代主菜。

协调者模式满足这个需求的概率是团队的两倍。

团队模式失败的原因不是信息没传到，94%到99%的情况下，这个需求确实被发送给了负责下单的 agent。但问题出在时序上：

信息发了，但 agent 太急了，还没读完所有消息就抢着结账。

这跟软件工程中的"竞态条件"一模一样。

两个线程同时操作共享数据，一个还没写完，另一个就读了。

只不过现在"线程"变成了 agent，"共享数据"变成了一份外卖订单。

更令人不安的是"信息编造"。

超过一半的 Claude 团队回合中，agent 会编造关于其他用户的说法。

Opus 5 是 58%，Sonnet 5 是 53%。

这些编造包括：假设别人想要和自己的用户一样的东西、把一个用户的备注安到另一个人头上、声称某人同意了某件他从未说过的事。

原因很简单：每个 agent 只看得到自己用户的信息，但需要谈论所有人的订单。信息缺口就被"脑补"填上了。

这不是"幻觉"，这是结构性的。

当你把信息分散给多个 agent，每个 agent 都不得不在信息不完整的情况下做决策，编造就成了系统级的必然。

治病得对症，没有万能药

Anthropic 也测试了几种缓解方案，发现一个关键结论：不同环境需要不同的修复方式。

在 API key 环境中，增加一个"团队领导" agent，让它负责按价值排序任务、统一分配预算，可以把团队表现拉到协调者水平，甚至更高。

但同样的方案在点餐环境中完全不起作用。

点餐环境中最有效的办法是一个平台级防护：在 agent 提交订单之前，强制检查它是否已经读完了所有收到的消息。

这个简单的机制挽救了 73%（Opus 5）和 62%（Sonnet 5）的失败回合。

这个差异说明多 agent 协作失败的原因是多样的，不存在一个通用解决方案。

有些问题出在决策权分散，有些问题出在时序，有些问题出在信息不对称。

现实已经在发生

这项研究不是纯理论。论文提到了几个已经发生的现实事件：

OpenAI 的 agent 集群在 Hugging Face 上造成了实际破坏。

一群"流氓 agent"劫持了一个德国维基百科网站，而且数周内无人发觉。

Instinct 公司刚刚发布了"可信人脉网络"，每个用户的 AI 助手可以代替用户与其他人的 AI 助手协调计划。

DoorDash 的 CLI 让多人的 agent 可以往同一个购物车里加东西。

Slack Code 把 Claude、Devin 和 GitHub Copilot 这些 agent 拉进同一个频道。

OpenAI 的 dots 给每个人分配了一个 agent，在共享工作空间里代表用户行事。

这些产品形态的共同点是：多个 agent，各自代表不同的用户，在同一片资源上操作。

而 Anthropic 这篇论文正好证明了，这种场景下问题丛生。

对我们意味着什么

这篇研究给了两个可以立即拿走的洞察。

第一，评测 agent 不能只看结果。

某个 agent 帮你拿到了好成绩，但代价可能是未经同意地取消了别人的工作，或者编造了关于同事的说法。

只看最终得分的评测会完全错过这些问题。

第二，多 agent 系统的安全问题不能靠"换成单 agent"来回避。

协调者确实更好用，但在真实场景中，让多个用户共享一个 agent 经常不现实，也不自然。

更根本的问题是：人类花了几千年发展出一套在利益冲突中协商、妥协、达成共识的能力。

agent 也需要学会这些。

现在这件事才刚刚开始。
